# Working in this repo (for agents)

Shared Sessions for Claude Code: a Claude Code plugin (`plugin/`, function hooks) and a small room server (`server/`). A person shares a Claude Code session with a link; teammates join from their own Claude Code. See README.md for what it does; this file is how to set it up and change it.

## Setting it up for someone

Use `scripts/setup.mjs`; it is non-interactive and safe to re-run. Every step prints one line, `OK …`, `NOTE …` (informational), `NEEDS HUMAN …` or `FAIL …`, and it exits 0 (all OK), 2 (a person must act) or 1 (failed). On `NEEDS HUMAN`, stop and relay that line to the person verbatim, then re-run the same command once they say it's done. Relay `NOTE` lines too.

It finds a Claude Code new enough for this plugin: `CLAUDE_BIN` if set, else `claude` on PATH, else (macOS) the newest one Claude Desktop bundles. If it FAILs on the version, set `CLAUDE_BIN=/path/to/claude` to a 2.1.286+ binary.

| The person wants | Run |
| --- | --- |
| only to join links teammates send | `node scripts/setup.mjs join` |
| to share (and join), and the team already has a server | `node scripts/setup.mjs host --server <https://…>` (includes `join`) |
| to share, and nobody has a server yet | `node scripts/setup.mjs deploy` (Cloudflare; prints the teammates' one-line install) |
| to know whether it works | `node scripts/setup.mjs check --live` |

What `check --live` proves:
- the plugin is installed and the saved server answers;
- the server can create, seat, serve and end a room;
- a real throwaway session shares using the saved setting, its room stays open when that session closes, and reopening it (`--resume`) to `/stop-sharing` ends it;
- a real throwaway session joins a room from its link.

Its throwaway sessions run in the system temp folder, and their transcripts are deleted afterwards. It can't see Claude Desktop's UI (the Share button, the Room panel): ask the person to look.

Facts that matter:

- **Joining needs the plugin and nothing else: no server, no account, no sign-in.** The link carries its server. The exception is a session shared with a team whose access is "Only people in the team": it needs a sign-in (`/team`) with an account in that team. Sharing uses the public server unless the plugin's `server` option (what `setup.mjs` sets) or `SHARED_SESSION_SERVER` names another.
- **Steps only a person can do.** Never attempt these yourself; `setup.mjs` stops at each with a `NEEDS HUMAN` line.
  - `npx wrangler login`, which is a browser OAuth approval.
  - Creating the Cloudflare account's `workers.dev` subdomain, once, in the dashboard.
  - Making the GitHub and Google OAuth apps for teams' sign-in on a server of one's own (README, "Teams on your own server"), and `npx wrangler secret put` of their ids and secrets: secrets a person pastes, never an agent.
- **A new `workers.dev` certificate takes a minute or so.** TLS handshake errors right after a first deploy are expected; `setup.mjs deploy` waits for it.
- **Claude Code 2.1.286+ is required** (function-hook plugins), or 2.1.285 with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` (early access there; `setup.mjs` sets it in the settings Claude Code reads: `$CLAUDE_CONFIG_DIR/settings.json`, else `~/.claude/settings.json`, its `SETTINGS`). 2.1.284 and older can't run it: they lack `session.append`. A `claude` on PATH can be older than Claude Desktop's bundled one; `setup.mjs` finds a new-enough binary (or set `CLAUDE_BIN`). Where the hooks module doesn't load (a version too old, a session started before the plugin was installed or updated, hooks switched off), `plugin/commands/share-session.md` answers `/share-session` instead with the fixes. Where it does load, the module answers the command itself under both names Claude Code lists, `/share-session` and `/shared-session:share-session`, so the markdown never reaches the model.
- **A session keeps the plugin copy it started with.** After installing or updating, *new* sessions get it; an open Claude Desktop session needs the app quit and reopened. `/reload-plugins` re-reads the same old copy, so it does not pick up a new version.
- **The plugin's commands** are `/share-session`, `/room`, `/who`, `/team`, `/invite`, `/share-file`, `/share-preview` and `/stop-sharing`. `/share-preview <port or http://localhost:port/path> [title]` lets teammates open a local web server at the same address. They are deliberately not `/share`, which is Claude's own.
- **Sharing sends the session's whole history.** That's prompts, replies, tool calls and the first lines of tool results, sent to everyone with the link and through the server. Before sharing an existing session for someone, tell them that. The plugin asks too: Share in a session with prompts offers **Share everything** or **Only from now on**, and `/share-session` there answers with `/share-session all` and `/share-session new` instead of sharing. A fresh session shares at once.

## Changing it

```bash
cd plugin && npx -y -p typescript@5 tsc -p .          # type-check against the engine's API (needs plugin/.claude/types, below)
claude plugin validate --strict plugin                  # what the engine and the plugin directory check
claude plugin test plugin                               # plugin/tests: UI tests (band.test.tsx, desktop + terminal surfaces) and the pure modules' (window, preview, proxy, upstream)
node test/setup.mjs                                     # setup.mjs against a fake CLI and a temporary home, the deploy order included (no model)
node test/local-preview.mjs                             # TCP helpers through a real Node room, real Chrome and Firefox preview windows and their WebRTC when installed (no model)
node test/browser-proxy.mjs                             # the preview window's SOCKS5 helper, its DNS-over-HTTPS against a local TLS fixture (no model; openssl for the test CA)
node test/discover.mjs                                  # same-project service discovery, and who holds a port (owner mode) (no model)
node test/tcp-worker.mjs                                # Worker TCP lifecycle and hibernation state, the Worker's public link, files and preview keys, both deploy orders (no model)
node test/peer.mjs                                      # messages and receipts between a guest's own sessions and the host's: the other side's peer=1 streams alone, never stored, their refusals, the Worker's routing by attachment (no model)
node test/mailbox.mjs                                   # the host's mailbox helper and relay/receipt.cjs through real Unix sockets: frames byte for byte, receipts both ways, strangers refused, started detached, gone with its Claude Code (no model; Node, macOS or Linux)
node test/previews.mjs                                  # preview shares, forwarding grants, Stop, needs, the public link's links, sessions, sockets and answers, bounded bodies and events, a worst-case meta, the home page's claims (no model)
node test/teams.mjs                                     # accounts and teams on the server, the sign-in's confirmation, Continue in a real headless Chrome when there is one (no model)
CLAUDE_BIN=$(which claude) node test/e2e.mjs            # real host + guests through a local server (needs model access)
EXTERNAL_SERVER=1 SHARE_SERVER=https://… node test/e2e.mjs   # …or through a deployed one
```

- `plugin/.claude/types/claude-code.d.ts` is the engine's API (copy it in from a Claude Code session with `/plugin-types plugin/.claude/types`; it is git-ignored). It is the authority on every hook, `$` call and element.
- **Engine rules the validator enforces:**
  - `$` may only be passed to functions declared at the top of `register.tsx`;
  - `atom(...)` references use literal plugin and key strings;
  - a link element accepts only `https:` (or `http://localhost`) addresses.
- **Behavior that shaped the design.** Don't undo these without new evidence:
  - **No long-polling from the plugin; updates come through a `curl` child.** While a plugin has a request in flight, the engine holds every prompt after the first until it returns. A child process's open stream holds nothing. So each shared session runs one `curl` (via `$.process.spawn`) reading `stream?after=<seq>`, one JSON line per room change. Riding turns read what it brings, too. Its address and token go to curl on stdin, never in argv. Without curl, or when the server has no stream, it polls: requests that return at once, every 0.4 s when busy, down to every 15 s when quiet.
  - **A host's step streams to guests while it runs, and only while someone's watching.** The host's `turn.step` passes each piece of the engine's stream to `liveFeed`: text, thinking, and a call being drafted go out as `delta` events (the room passes them on and never stores them; `send` joins pieces of one kind until the next post, 250 ms), and none at all when nobody else is online in the room. A call being drafted goes as a progress line (`drafting`: the tool, what it's for from the start of its arguments, `draftTarget`, and its length every 2,000 characters), never its arguments, which come whole in its row. A guest's ride yields the host's thinking as `thinking` chunks (the engine shows them live and doesn't record them; blocks numbered as they come, so thinking precedes the words), and its working line and the row above the prompt say what's happening this moment (`doing` on `working`: Thinking, "Writing notes.md · 4k characters", "Running npm test"). A plugin's tool card only exists once its call is made, so a call can't be streamed into a card. Older guests ignore the new kinds of delta.
  - **No prompts from inside another hook's dispatch.** A prompt submitted there is refused, so the plugin's prompts go out from a timer (`submitLater`; a host's teammates', `nextGuestPromptSoon`).
  - **No running its own commands for output.** A plugin's own `$.command.run` skips that plugin's command hooks, so guest transcripts are drawn by riding turns (`turn.step` answered from the room, no model call) instead.
  - **Strip the app's context.** Claude Desktop puts a `<system-reminder>` into a first prompt. `typedText()` strips it before matching links or forwarding prompts.
  - **A guest forwards what a person typed, and their own sessions' messages.** A guest's prompt goes to the host's Claude from `GUEST_SENDS` origins (the prompt box, Desktop/SDK, Remote Control, an unattested same-user socket, a click's follow-up), never `isMeta`. A message from another of the guest's own sessions on that computer (A; `OWN_SESSIONS`: `peer`, `peer-send-message`, i.e. `SendMessage` to the joined session G) reaches G as any session's does: Claude Code's own inbox queues it, holds it while A runs in another permission mode class (Desktop's Deliver/Deny; `cause=mode-mismatch` in its debug log), and cuts duplicates, floods and loops. Nothing takes it earlier (no `session.receive` hook): with `prefs.relayPeers` on (Room → Settings → Messages from my other sessions), `prompt.submit` lets it in (`next(e)`, so G's transcript keeps Claude Code's row for it) and, from a timer, sends it on (`relayQueued`): the row's `origin.msg_id` and `origin.hopChain` are read from G's transcript (`peerRow`: `tail` of `projects/*/<session id>.jsonl`, the newest `kind: peer` row from that address with those words not taken already, every 100 ms for 2 s, since Claude Code writes it about 150 ms after the prompt enters; not found, a new id and no chain, and A gets no receipts), and `POST peer { handle, name, mode, chain, id, pid, body }` carries them with A's name (`tidySender`), its mode class (`from-mode`) and a handle in its address's place (`keepRoute`: 32 hex, one per address and seat, `peerRoutesA` kind `guest`, saved with the place and cleared with the room; the address never leaves G's machine). G's turn for it is an own ride (`kind: 'own'` with that `pid`), as a typed prompt's is: it plays the host's turn for it, which the host's plugin tells by the pid (`turn` events' `pid`, and a `user` row's when it went into a turn already running there, which the ride then takes as its own). It is never a note ride followed by rides: Claude Code gives a send from a session the hop chain of that session's newest user row, and only when that row is a peer's (2.1.304's `$Qe`), so a plugin prompt entering G before G sends A the host's reply would strip the chain, and with it A's and G's loop guard. One delivered into a turn playing in G (`e.turnId`, or `delivered()`'s `midTurn`) goes on with no turn of its own. Where it can't go, A is told from G (`tellPeer`: `$.session.send` to A's address, from a timer) and the ride ends in the same words (`endRelay`, `unsent`): no room, watch-only, the host away, a server without `peer`, a Claude Code older than 2.1.304 or without `CLAUDE_CODE_MESSAGING_SOCKET`, a system other than macOS or Linux (`peerMissing`, `relayRefusal`), the room's answer (`offline`, `unsupported`, 429, 413, 410: `peerRefusal`), a place late coming back, the host's side declining it (a `declined` event with the pid, `declinedRelay`), the host's Claude Code holding, dropping or refusing it (its receipt, `guestReceipt`), or 10 minutes with no host turn for it (`RELAY_WAIT_MS`). With `relayPeers` off it's kept in G with a note ("A message from **…** stayed here"; mid-turn a toast and `{ drop }`, `keepHere`). The relays (`peerRelaysA`: id, pid, handle, address, whether the id is A's own, `held`; the newest 64) let the host's Claude Code's receipts reach A: `relay/receipt.cjs` (a one-shot Node child, its input on stdin) writes Claude Code's own `peer_message_status` line into A's socket from G's (`refused` written as `expired` with `status_detail: "refused"`, a drop with its reason, `delivered` only after `held`, only for the id A gave it). A's Claude Code takes one only while that send is still open there: a message G itself held (A in another mode class than G) was settled by G's own receipts, so A's Claude Code drops the host's ("no outstanding send matches" in its debug log), and A hears only that G let it in. The host's turn for a message the host's Claude Code held plays in G as any host turn (its own ride ended at the hold), so G's reply goes with no hop chain: a loop through a hold starts its chain again, each round waiting on a person's Deliver. One without a sender's wrapper isn't relayed, nor an agent's own delivery (`agentId`) or a team's mailbox (`teammate`); a channel's (Slack, OpenClaw), a task's or a schedule's message stays in the guest's session. Before 0.11.23 a guest's agents couldn't reach the host at all, 0.11.23 relayed nothing (it required `isMeta` unset), and 0.11.24 and 0.11.25 relayed none from a session in another mode class (taken from `prompt.submit` as a prompt of the plugin's, which the receiving engine held until shutdown).
  - **The host's Claude answers a teammate's session natively, through a mailbox.** The host's side runs one helper a room (`relay/mailbox.cjs`, `runMailbox`): a launcher started through `FIND_NODE` spawns `mailbox.cjs --serve` with `detached: true` (a session and process group of its own), hands it its settings on stdin (`room`, the host token, `version`, a 256-bit `controlToken`, `dir` and `own`: this session's socket and its folder, `pid`: this Claude Code), relays its `{ state: 'ready', port, pid }` and exits, and the served helper writes nothing until its parent has gone (`detached()`): Claude Code takes a frame from a process of its own tree as its own, so a mailbox that is its descendant would be no other session to it. Its pid and port are in `$.state` (`mailboxHelperA`). Commands go to its loopback control port (`controlServer`, `controlPost`, 256 KiB a body): `open`, `close`, `deliver`, `receipt`, `exit`. A mailbox (`ss-<32 hex>.sock` beside this session's own socket, `/tmp/cc-socks` and the like) stands for one of a teammate's sessions, by the seat and handle the room brought its message with (`peerRoutesA` kind `host`: `{ seat, handle, who, name, at }`, keyed by the mailbox's own id, so another seat's copy of a handle is another mailbox). `deliver` writes the frame Claude Code itself writes (`msgV: 1`, `msg_id` the teammate's message id when it is one, `type: 'user'`, the envelope with `from="uds:<mailbox>"`, A's `hop-chain`, `from-name="<name> · via <who>"` and A's `from-mode`, `priority: 'next'`; no auth line, which only Windows asks for), so the host's Claude Code queues it, holds it across a mode class, cuts a loop by A's chain, frames it with its own guidance, and the host's Claude's `SendMessage` to `uds:<mailbox>` comes back to the mailbox; nothing of the plugin's hooks into that send. What a mailbox hears is taken only from `uds:<own>` (this session; anyone else's frames are refused): a message goes `POST peer { to: seat, handle, body, ref }`, Claude Code's receipt for one it held or dropped `{ to, handle, status, id, reason }`, and a forward the room doesn't take is answered into this session as a receipt from the mailbox (`refused` for a server or guest that can't, or a room gone, else `dropped`, `rate-limited` when too many). The guest's receipts (A's Claude Code's, from the delivery notices G's Claude Code gives it: `[Cross-session delivery notice] …`, answered `{ text }` so nothing enters G, parsed by `noticeOf` and matched to G's sends in order, `takeNotice`) come back on the host's stream and go into this session from the mailbox as A's Claude Code wrote them (`hostReceipt`, `delivered` only after `held`). A notice names its sends as " (recipient: <address>; msg_id: <id>)", or "2 recipients: …", three addresses and five ids at most. Where the host's side can't take a message (no Node, a system the helper can't run on, a mailbox that can't open, a delivery refused, watch-only, an older engine), the teammate's turn for it is declined (`declined { pid, who, reason }`), which their plugin says to A. Its turn here is "<who>'s agent" with the teammate's pid (`relayPidOf`), the row the room keeps is a relayed prompt under the teammate's name (`mailboxRows`), and a row naming a mailbox names the session it stands for instead (`hideMailboxes`): no mailbox path reaches the room. A message from a mailbox is the host's Claude's like any peer's: the host's mode decides its calls. The helper ends, unlinking every mailbox, on SIGHUP, SIGTERM or SIGINT, once this Claude Code is gone (`process.kill(pid, 0)`), or when told (`exit`, the room's end, `finishMailbox`), and sweeps `ss-*.sock` that refuse a connection and are over 60 s old as it starts. A reload ends the module before's helper (`endOldHelper`: its pid, its command line checked for `relay/mailbox.cjs --serve`) and opens the same mailboxes in its own (`restoreMailboxes`). The room (`POST /api/rooms/:id/peer`, `peerRoute`) passes a guest's message or receipt to the host's streams that said `peer=1` and the host's to that seat's alone, never stores, broadcasts or keeps any in history, checks each (`peerProblem`: the handle's grammar, statuses `held`, `denied`, `delivered`, `expired`, `refused`, `dropped`, a reason only with a drop, uuid ids, a chain of 32 tokens at most) and answers `{ delivered: true }` or `{ delivered: false, reason: 'offline' | 'unsupported' }` (403 a `to` that isn't a guest seat now, 429 past 60 a minute a seat and 120 the host, `PEER_LIMIT`); a room says `peer: true` at create and join (`ShareRoom.peer`). This leans on what Claude Code 2.1.304 doesn't document: its socket frames and their folder, receipts' `peer_message_status` lines, the delivery notices' words, the transcript row's `origin.msg_id` and `hopChain`, a plugin's send taking the newest peer row's chain, and a mailbox name its own socket pattern doesn't match (`ss-…`) still being dialled; `test/mailbox.mjs` pins the frame and receipt bytes. What it leaves: on the host, the helper and its `ss-*.sock` files while the room is open; in G's transcript and on its screen, A's messages, the host's replies as G's sends, Claude Code's line for each receipt, and "Prompt not submitted: a hook answered without passing the prompt on" for each delivery notice the plugin answers (the engine writes that for any prompt a hook answers without passing on, and has no quieter answer); in A's, G's messages and receipts from G's socket. Checked live on 2.1.304 in terminals on macOS (two homes, a local Node server, Haiku): an answer and a follow-up through G's own socket, the hop chain growing a token a hop, two senders on mailboxes of their own, holds and releases reported both ways (a bypass session on each side), a counting game cut by G's Claude Code as a loop at its 21st message, a resume reopening the same mailboxes, and no `ss-*.sock` once H exits. Out of scope: `SendUserFile` and `notify_when_idle` to a mailbox, the host's Claude writing first to a teammate's session it has no mailbox for, and Windows.
  - **An event the room refuses as too large is dropped, never sent again.** A post of events refused with 413 (a guest's event past 128 KB, `EVENT_BYTES`; the room takes nothing of that post) goes again one event a post (`singly`), so the one too large is found; that one is dropped and said once a room ("A message was too large to send to the room."), and everything after it goes on: sent again, it would hold back the whole outbox. A prompt typed here that was refused never runs on the host's side, so its turn here ends at once saying so ("This was too large to send to **Sam**'s session, so it didn't go to Claude.", `tooLarge`, `unsent`), and it no longer holds back the host's turns after it (`ownPending`). The plugin keys on the status alone, so an older server's 413 for a body too large is handled the same. A host's event is never refused: the room cuts it to fit (`fitBody`, below).
  - **Newer engines raise more than 2.1.295 did.** From 2.1.300 a subagent's run raises `turn.start` (with `agentId`), and a prompt typed mid-turn reaches `session.append` twice, as it's queued (door `queue`) and as it goes in; the host's hooks skip the first of each, or a subagent's brief went out as the host's prompt and its working line never cleared. 2.1.295 refuses a whole tree with a prop it doesn't know (`Text` `weight`/`size`/`mono`/`tabular`, a named `gap`), drawing the engine's own instead; the engine's version is in `$.env.get('AI_AGENT')` (`claude-code_2-1-300_…`), so a newer prop goes only where that says it's understood.
  - **Showing things in a guest's Claude Code happens in a turn.** A plugin's own call to a viewer, outside any turn, shows nothing: `SendUserFile` reports "delivered" but nothing opens, and auto mode refuses widgets and the browser pane. The same call made as a step of a turn (`turn.step` yielding a `tool` chunk) opens in Desktop's own viewers. So riding turns replay what the host's Claude showed as tool steps. The Files pane (`ccd_view.show_pane`) is the exception; it opens from a plugin's own call, which the Room panel's Open uses for a file. A preview's Open and a shared page's Open call Claude's browser themselves (`Claude_Browser.preview_start`, `inPane`), outside a turn; auto mode's refusal there sends them to the person's own browser or the Files pane (below, "Auto mode refuses").
  - **A guest session never calls its own model.** Every turn there is a ride the plugin answers from the room. Rides are matched by the turn's text, then by its beginning, then oldest first, because the text a turn starts with can differ from what the plugin submitted. A turn that still matches nothing gets a short local note from `turn.step` without `next`, never a model call. Every later step of a guest's turn is answered too: a Stop hook in the guest's own settings can make the engine continue a turn the ride already ended. So is a note's turn, whatever the mode (a place late coming back is idle): `turn.step` answers a note ride before it reads the mode, its first step the note and every later one nothing, never `next`.
  - **A riding step gets 10 s of its own time.** Each `turn.step` dispatch's budget counts the hook's own time, plain timers and `$.clock.sleep` included, and past it the engine runs the model in the hook's place: in a guest, that is the guest's own Claude answering the host's prompt on the guest's machine. A host's Claude can be silent far longer (a slow tool, a long think over a big context), so a ride waits through `pause()`, a `sleep` child, because the clock stops while a `$` call is in flight. The hook's `.catch` is the backstop: a guest step that throws or overruns ends quietly, and the host turn it was showing plays again after it. It takes a ride of the room as a guest's whatever the mode says by then (a Leave sets the mode idle as it begins, with a ride still running): the ride is read before the mode (`ridesByTurn`), and only a subagent's step, or a turn that is no ride of the room (or only a local note) while the mode isn't `guest`, goes on to the model.
  - **Pictures in tool results travel as room files.** A result's image blocks (a browser-pane or computer screenshot, an image `Read`) are taken from the row (`media`, never sent), uploaded (`upImages`, three at a time, under "What Claude shows") and named on the row by file id (`images`); the row waits in the outbox (`hold`) and everything after it waits too, so events stay in order without holding the turn. A guest's replay answers with an array of blocks, text and `{ type: 'image', source: { type: 'base64', … } }` (`withImages`, downloaded once per id): a registered tool's result may be a string or such an array, which the transcript keeps as the tool's image result and Desktop draws in the card; MCP's `{ data, mimeType }` shape is refused by the API. A shared history carries the newest 60 results' pictures. The terminal says them as it says its own (`Read image`, `[Image]`).
  - **A published page travels with its files.** An Artifact publish uploads the page and its `files` (a map or list, sources relative to `root`), each tagged with its place beside the page (`path`, made relative and inside by `pagePath`), as one `page` event. A guest saves such a bundle in a folder of its own (`.shared-session/<host>/page-<id>/`, `downloadShown`), each file at its place, and opens the page in the browser pane, where a page inside the project runs live and its relative `img/…` resolve; the Room's Open does the same (`openShown`; refused there by auto mode, the Files pane, said once). A page alone still goes as `send`.
  - **Claude asking for the share command gets the plugin's answer.** The model can invoke `/share-session` as a skill (`Skill`), which skips command hooks and would read the markdown fallback ("the plugin isn't running"). A `tool.call` hook on `Skill` answers it with the forked result shape (`{ success, commandName, status: 'forked', agentId, result }`, which passes Skill's output check) saying where things stand (`shareAnswer`); Claude never starts sharing itself. A page Claude publishes or opens again while hosting adds a note to its result (`context`) that it already went to everyone, so Claude doesn't send people after the private claude.ai link; an `open` re-sends the page with its files (`pagesA` by artifact id, else the newest publish in the transcript, `earlierPage`).
  - **The update command typed by a guest runs on the guest's computer** (`UPDATE_TYPED`, `updateHere`: `claude` on PATH, else Desktop's newest, with HOME and PATH passed), never sent to the host's Claude; a folder copy then catches up and reloads in place, otherwise it says to start a new session.
  - **The room knows everyone's plugin version.** The server keeps each seat's version from its requests (`x-shared-session-version`, on the curl stream too) and the host's, lists them in `people`, and wakes the room when one changes; the Room says "on X, needs an update" beside anyone behind the newest known (`latestKnown`), and the host hears it once per guest with the update command (`noteBehind`).
  - **A guest's attachments travel as room files.** A prompt's hook sees only its attachments' kinds; their bytes come with the guest's own stored message (`session.append`, door `prompt`, a person's origin), so the prompt waits for it (`heldPrompt`, 8 s at most, then goes with its words alone and says so), its images and PDFs go up as room files (guests may post files), and the prompt goes with their ids. The host saves them under `.shared-session/<guest>/` (`saveAttachments`) and names each in the prompt with how to see it (`📎 path (attached by …; open it with the Read tool to see it)`): a plugin's prompt carries words alone, a hook can't add media to a stored row ("carries media"), and a plugin's own `prompt.submit` hooks don't run for the prompts it submits, so the words are the only way to tell Claude. Read shows the picture in a card, to the guests too.
  - **Host tool calls replay as cards of the plugin's own tool, never the real one.** A guest's ride yields each host tool call as `mcp__shared-session__replay` (registered on join), whose `tool.call` hook waits for the host's result row (paired by tool_use id) and returns it; its `.catch` answers too, so nothing beneath ever runs. The `ToolUse` render hook draws it as the call it replays (`tool` rewritten to `Bash`, `Read`…). Answering a built-in tool's call instead would be checked against that tool's output schema, and a result that fails the check lets the real tool run on the guest's machine. Viewer calls (files, widgets, pages) are still made again for real (`replayOf`), so their rows stay out of the card replay.
  - **A join's history is a turn per earlier prompt, two steps each.** Only a turn shows a prompt as the person's own message (`$.session.append` takes notes alone), so each exchange is a ride: one step with its text and every call as a replay card whose result is preset from the room (`historyBlocks`, `hostCalls`), the next with its last words (`staticRuns`). Never a step per call: 25 prompts and 300 calls land in about 3 s.

A server reached but slow once TLS is up (`SLOW`: a slow domain, or a name made slow on purpose) or giving a bad answer (`PROTOCOL`) is that name's failure alone: the next server is asked, none is skipped, and that name goes by its local answer for 30 s (`dohMiss`); a server cut short by the look's 6 s isn't judged (`SHORT`). Otherwise one slow name would send every other name to its local, possibly poisoned, answer. The order stays Cloudflare then Google, and DoH starts only after the local answer allows the name, so a name the local answer refuses (loopback, the network) is never sent to them. That, not the local answer, is the one that counts where an upstream is needed: the local resolver may be poisoned or blocked (Google's sign-in from China). The local answer still decides first: loopback routes to the host's shares, and an own, local-network or tainted answer is refused, never tunnelled. A DoH answer holding any refused address (loopback included) refuses the name; DoH unreachable, a bad answer (another status, a record that's no address, too large) or no records falls back to the local answer's checked addresses; with neither, the name is refused (04) and the upstream never sees it.   - **Teams live in the server's directory, and rooms only ask it.** `server/teams.mjs` (`Directory`, over a key-value store: a Durable Object's storage on Cloudflare, `DATA_FILE` on Node) holds accounts, teams, invites and each team's list of open sessions. A room asks it two things, `shareCheck` (may this account share with this team) at create or `POST rooms/:id/team`, and `joinCheck` (the team's access as it is now) at every join, and tells it `register`/`unregister`; on Cloudflare those go over `/rpc/*` on the directory's stub, which the Worker never forwards from outside (`Directory.owns` lists the public paths, `/auth/confirm` among them). A list asks each room for its info and drops the ended and expired. One account makes at most 30 changes a minute (`CHANGES`, counted in the directory's memory, `change`: team edits, invite links, removals, invites taken or sent, `sessionInvite` included), past which 429; signing out and deleting the account aren't counted. Removing someone writes `left:` only for a member, and `updateTeam` writes only the keys that changed and looks only at accounts a newly added domain (through the `email:` index) or organization (one read of the accounts) takes.
  - **A sign-in's token never travels in an address or argv, and only the browser's Continue signs in.** The plugin opens `/auth/<provider>/start?login=<sha256 of a secret>&code=1` (`startSignIn`; `code=1` says this version shows the code, so the server's page asks that the two match; a link without it, 0.11.24's, gets the page without the code), and collects the token by POSTing the secret to `/api/auth/poll` every 2 s (delivered once; the server keeps only hashes of tokens). Whoever makes a start link chooses its `login`, so without a confirmation someone could hand a person their own link and collect that person's sign-in: the provider's answer (or the test provider's start) only asks. The directory keeps who it is as `login:<hash>` `confirm`, with a nonce, and shows "Finish signing in" (`ask`), with `code=1` the code `XXXX-XXXX`, the first eight hex of `login` in capitals, which the plugin shows too ("Your browser will show the code XXXX-XXXX: continue there only if it matches.", `signInCode`, `codeSaid`: in `/team signin`'s reply, in the Team panel while it waits, and in a toast as the browser opens). Only its Continue, a form POST of `login` and the page's nonce to `/auth/confirm` (`confirm`; a wrong or missing nonce is 403, an unknown or expired sign-in 410), signs in (`finish`), and `done` keeps the account id and no token: the token is minted at the poll that collects it (`poll`, `mint`), so storage never holds one, and a poll of an expired sign-in deletes it. The page is never framed (`frame-ancestors 'none'`, `X-Frame-Options: DENY`), cached or sent as a referrer (`guarded`), and runs one script, allowed by its hash (`CONTINUE_SCRIPT`; `script-src 'sha256-…'`, never `'unsafe-inline'`), which keeps Continue disabled until the page has been shown and focused for 400 ms and the pointer has moved over it since (a move that goes nowhere doesn't count), or a key is pressed after those 400 ms; losing sight or focus starts it over. So a page that raises this one under a person's double-click can't have the second click continue. A tap makes no pointer move (a drag or a scroll does), and some assistive technology clicks without one: Tab, then Enter or Space, works after the 400 ms. Without script, a `<noscript>` Continue is enabled. The token is saved per server in `${CLAUDE_CONFIG_DIR || HOME + '/.claude'}/shared-session/account.json` (`accountFile`, from `configDirOf`, as the checkpoints are) through `sh` with `umask 077` (`writeSignIns`, for `saveSignIn`; the JSON on stdin). With `CLAUDE_CONFIG_DIR` set and no file there yet, the first read copies the sign-ins of `~/.claude/shared-session/account.json` into it the same way, once (`readSignIns`, from `homeAccountFile`: where 0.11.24 and older keep them whatever the folder; a file there, even empty or unreadable, is never copied over), and leaves that file as it is, for 0.11.24 and older and the folders still reading it. Signing out or deleting the account clears the folder in use alone: the copy holds the same token, so the other folder's next look at the server gets a 401 and clears its own (`refreshTeams`: "Your sign-in ended. Sign in again."). The token is sent only to the server that gave it: `Authorization` for the team API, `x-shared-session-account` on a share or a join. `SHARED_SESSION_NO_BROWSER=1` opens nothing and raises no notification (the e2e reads the link from `/team signin`'s reply instead); `AUTH_TEST=1` on a Node server adds the `test` provider, which asks for whoever its link names: the e2e and `test/teams.mjs` post its confirmation form, and `test/teams.mjs` presses Continue in a real headless Chrome, Edge, Brave or Chromium when it finds one.
  - **Invites go to accounts, and a machine asks for them once.** A host invites teammates (`POST rooms/:id/invite`, the room's host token plus the host's sign-in; the directory takes only people who share a team with them) and the directory keeps one per person and room (`sinv:`, 12 hours, dropped when the room ends). Inviting again replaces it with a new time, so it comes back for someone who set it aside and counts as new on their machine (an invite is known by room and time, `inviteKey`: notified again, said again); the Room keeps **Invite again** beside "Invited 2m ago" until they're in. Every session reads a shared copy in `$.store` every 10 s (`pollInvites`, `INVITES_KEY`), and the one that finds it older than 30 s asks `/api/me/invites` for the machine, so ten open sessions make one request. An idle session's row above the prompt shows the newest ("Sam invites you", **Join** the one primary, **Dismiss**); a session that's in a room (every open session can be) shows it as a button in its own row, in place of Invite and Copy link, which opens the Team panel's Live page, and says it once in a toast (before 0.11.14 it showed nowhere there); the Team panel lists all of them; answering one drops it on the server and in the shared copy (`dropInvite`), and Join joins the way the Team panel does (`joinInvited`). The session that fetched new ones raises a notification for each, once for the machine (`notified` in the shared copy, `notifyInvite`): `$.ui.notify` where a terminal channel sends it, else (Claude Desktop has none, `no-surface`) `osascript display notification` or `notify-send`; off by the store's `inviteNotify`, and never under `SHARED_SESSION_NO_BROWSER=1`.
  - **"Join" joins here only in a fresh session.** A session that is idle with no prompts joins in place (`joinHere`: `join`, then a ride as pasting the link gives); anything else opens a new Claude Desktop session with `claude://code/new?q=<link>` (Desktop prefills the prompt, it doesn't send it: the person presses Enter), or in a terminal copies `claude '<link>'`. Desktop's own `start_session` tool is gated and takes a Claude task brief, so it's not used. A session holds one room, so **Join all** is a session per room, and since Desktop holds one new-session draft at a time (a second `code/new` replaces the first), the rest wait in `$.store` (`JOIN_QUEUE`: the room being joined, the rest, ten minutes) and the session that joins one opens the next (`continueJoins`).
- **Release:**
  1. Bump `plugin/.claude-plugin/plugin.json` `version`. Claude Code updates by version, not by commit: a push without a bump reaches nobody.
  2. Run the checks above.
  3. Push to `main`, then deploy the server, in that order. On an update, deploy the preview Worker first (`npx wrangler deploy -c wrangler.preview.toml`, then `npx wrangler deploy`): new rooms' preview links name a key only the new preview Worker routes, and it still routes what older rooms made. The first time, the main Worker goes first, since the preview Worker's `ROOMS` binding names the main script's `RoomObject`. `node scripts/setup.mjs deploy` does both (an update is a main Worker that `wrangler deployments list` finds; if that can't be told, the first-time order), and on an update stops with FAIL before the main Worker if the preview Worker's deploy fails, by wrangler's exit status (a preview Worker on a custom domain prints no workers.dev address, and that's no failure). The server reports the version it was deployed with as the newest; plugins that update in place download `main` when that's newer than theirs, so `main` must already have it. The others show "Version X is out" against it. Installs with the marketplace's `autoUpdate` on (Room → Settings → Updates, or what `setup.mjs` sets) update within minutes of a session starting; others with `claude plugin marketplace update claude-share && claude plugin update shared-session@claude-share`.
  4. When an older version must stop being used (it misbehaves), raise `PLUGIN_MIN` in `server/core.mjs` and deploy *after* the push: the server then turns that version away from sharing and joining, with the update command in the message. Every plugin sends its version as `x-shared-session-version`; one that sends none is older than this scheme and counts as too old.
  5. Rolling the main Worker back past 0.11.25 keeps a room's files only as far as its `meta` lists them: 0.11.24 reads files from `meta` alone, where 0.11.25 keeps the newest 512 records (`META_FILES`, `metaOf`), so in a room with more the older ones are 404 until it's rolled forward again (every record is under `bm:`); rooms last 24 hours. Drop `META_FILES` once nothing will roll back to 0.11.24 or older.
- **Server:** `server/core.mjs` is shared by `node.mjs` (Node 20+) and `worker.mjs` (Cloudflare Worker + Durable Object, deploy with `npx wrangler deploy`). What the two must agree on lives in core (`PUBLIC_LIMITS`, `TCP_LIMITS`, `revokeMatches`, `publicPairValid`, `tcpStep`, `mergeTCPStats`); the adapters keep only sockets, timers and persistence. Every body is read through one `readBody(req, max)`, counted in bytes as it arrives; Node also bounds each buffered body per route as it arrives (`bodyMax`: the preview port's `PROXY_BODY_MAX`, the directory's, a file's `FILE_MAX`, a JSON route's `JSON_BODY_MAX`, from `bodyLimit`) and refuses a declared length past it before reading any, while streamed routes (`streamedRoomBody`: shares, stops, grants, links, needs, replies, proxied answers, rejects) bound themselves, and a grant or a stop reads none. The outer Worker buffers no room body: on a route that isn't streamed, a declared length past its bound (`bodyLimit`: 1,536,000 bytes for JSON, 10 MiB for a file) is refused 413 (`bodyTooLarge`) before the room is asked, and every body goes on as a stream (`duplex: 'half'`) that the room reads through `readBody`. A directory body, which the directory reads whole, the Worker reads itself, bounded at 3 × `BODY_CHARS` (`DIRECTORY_BODY_MAX`, node.mjs's `bodyMax` for it; no content-length required), and hands on whole. Keep `wrangler.toml`'s `compatibility_date` no newer than the wrangler you deploy with supports.
  - **Nothing runs on a timer while a room is quiet.** Who is still here is settled by the next request, or by an alarm a disconnect sets for when its 45 s grace ends. The other timers are the room's expiry and, for what a preview holds open, a TCP grant's expiry and a socket's session expiry or pairing deadline (the Worker's one alarm, `schedule()`; Node's per-pair `armTCP`, `armPublic`). A link or browser session that expired with nothing open on it waits for the room's next activity (`sweepGrants`), or goes with the room: no alarm is set for it, and the home page says so. The Worker writes its alarm only when what's due is sooner than the one set (`schedule`, `alarmAt`, read back with `getAlarm` as the object wakes): one set for later fires early and `alarm()` sets the next, so a TCP connection or a stream's turn writes none of its own.
  - **A seat let go comes back.** A guest with no connection for 45 s (a laptop asleep, a network gap, routinely) is let go (`sweep`, "lost connection" in the Room), but its token is kept (`away`, the newest 100, stored with the room) and seats it again as it was the next time it's used (`comeBack`, from `auth`). Before this, the next request got a 401 and the plugin told the guest the session had ended: that was most of "everyone keeps dropping". The plugin also takes a new seat itself on a 401 (`reseat`, `stillSeated`: the stream, a poll, or the outbox, whose batch is kept and sent again), and only a room that's gone (404, 410) or a join it refuses ends its place. A reseat is no way out of the room for what runs here: listeners, the window and its proxy go on, and only requests made with the old seat's token end (`RoomScope.token`, `sameRoom`). Leaving on purpose (`left`) isn't kept, and it, like a seat dropped from the away list, takes what the seat was given for previews (`revokeSeat`: its TCP grants, its browser sessions and their public sockets, and its links, used or not); a seat away within its grace keeps them.
  - **One person, one entry, wherever they are.** A share and a join carry the person's sign-in when there is one (`x-shared-session-account`), so the room knows seats by account: `people` lists a person once with all their `seats` (the host's own other sessions fold into the host), a second session of theirs adds no "joined" and its leaving no "left" while another stays, a team's `sessions` list who's in each by account (`accounts`), and invites skip people already in. The plugin finds itself by `seats` (`isMe`). On one computer, each session in a room writes `live:<room>:<session>` to `$.store` (`holdRoom`, at share, join, resume and every minute; three minutes unwritten is gone): a pasted link, the Team panel's Join and an invite's Join open the session already in that room (`openHeld`, `claude://claude.ai/epitaxy/<Desktop id>`) instead of joining twice; the same link pasted again within two minutes joins anyway. The Team panel shows **Open** for those, says "you're in it elsewhere" for rooms the account is in on another computer, and **Join all** and the Team button's count leave out everything that's already yours.
  - **On Cloudflare, streams end at the Worker, not the Durable Object.** A Durable Object holding an open HTTP response is billed for every second. So the Worker holds the client's stream and talks to the room over a WebSocket the object accepts with the hibernation API; the object sleeps between changes. A closing socket is still listed by `getWebSockets()` while its close is handled; `worker.mjs` tracks closed ones itself. A change goes to the stream sockets alone (tagged `stream`, `broadcast()`): TCP and public channels never read room JSON, so their attachments aren't even opened for it. The object sweeps expired grants, browser sessions and links, with their channels, from its alarm and constructor (`cleanupTCP`, `cleanupPublic`; an ordinary request sweeps in `roomRequest`, `sweepGrants`), and closes stale halves right before admitting another (`closeStaleTCP`, `cleanupPublic`).
  - **Every stream ends itself after 5 minutes** (`STREAM_MAX_MS`), and the plugin reconnects at once. Presence doesn't depend on noticing a dead connection (a sleeping laptop's can look alive for many minutes): a client that's gone just never reconnects. A stream that ends within a minute backs off instead, so a proxy that cuts streams short isn't hammered.
  - **A room loaded from storage starts its seq numbers past any it may have handed out** (`Room.resume`), because live events (deltas) are never stored.
  - **Events are bounded in bytes.** Every string in an event's body, at any depth, is cut at 32,000 characters, and nothing nests past 32 levels (`clampBody`, `BODY_DEPTH`: JSON.parse takes any depth, and JSON.stringify, which recurses, would throw wherever the room is sent or saved). A body is at most 128 KiB serialized (`EVENT_BYTES`; the plugin's largest row, a reply of 32,000 CJK characters, is about 96 KB): a guest's post with one past it is refused 413, "An event is limited to 128 KB.", nothing of it applied, and a host's event is cut to fit, never refused (`fitBody`: its strings halved down to 64 characters, else `{ cut: true }`), so no host's outbox, 0.11.24's included, sends one again and again. A room keeps its newest 5000 events and 16 MiB of them (`HISTORY_LIMIT`, `HISTORY_BYTES`, counted as they come and go, `trimEvents`; a room loaded larger is cut to it), and 400 live ones and 2 MiB of them (`LIVE_LIMIT`, `LIVE_BYTES`). A room holds 128 open previews (`ROOM_PREVIEWS_MAX`; past it, 429).
  - **A room's files are kept beside their bytes.** On Cloudflare each file's record (`id, name, type, size, ts`) goes under `bm:<id>` with its chunks, in one `storage.put`, and the object reads the records back from `bm:` as it wakes (`loadFiles`). So a room holds up to `ROOM_FILES_COUNT` files (10,240: 100 MB of 10 KB files) within `ROOM_FILES_MAX` (100 MB), more than its one `meta` value (2 MB at most) could list. `meta` keeps the newest 512 records as well (`META_FILES`, `metaOf`), in the shape 0.11.24 kept all of them: 0.11.24 reads files from `meta` alone, so a main Worker rolled back to it still serves those (Release, step 5). On load a record in `bm:` wins: `meta`'s counts only for a file whose `bm:` has none, one 0.11.24 uploaded (before 0.11.25, or after a rollback to it), and moves beside its bytes then. A file's type, like its name, is kept without control characters (`fileType`, `fileName`), so a worst-case `meta` with its 512 records stays under 1 MiB (`node test/previews.mjs` measures it). Node keeps every record in its one data file.
  - **Node keeps one process for every room, so nothing a client sends may end it.** Its upgrades are guarded (`upgrading`: an error listener on the socket first, since Node takes its own off a socket it hands over and a client resetting a refused handshake would end the process; then a try/catch that refuses with 400); the preview port builds its Request on a fixed host (`http://preview.local`), reading only the path, query and cookie, never a Host the URL parser might refuse; and a debounced save that fails (a full disk, a snapshot past what one string holds) is logged, never thrown from its timer (`later`), while one a request waits for still fails that request.
  - **Previews run on a second Worker from the same script** (`wrangler.preview.toml`, `ROLE = "preview"`), its own workers.dev host name, so an app's root-relative paths work. A ticket (a link: 10 minutes, its pid, path and minting seat) is kept with the room (`room.tickets`, through a sleep or a restart) and becomes a cookie there (`enterPreview`); it lets in one browser, which may use it again (a reload, a reopened pane) while its browser session lasts, and no other. Minting is 30 a minute per seat and 120 per room (`mintAllowed`, in memory, counted before the body is read), and a seat keeps its newest 16 links, a room 128: past either the oldest goes, used ones first (`mintTicket`, `dropOldest`), never a 429, and the second link after clearing counts like any other. A link's page is percent-encoded outside printable ASCII (and backslashes, which browsers read as slashes), 2048 bytes at most, else `/` (`linkPath`, as it's made and again as it's used), so its redirect can't throw, and `enterPreview` makes its answer before it spends the link or makes a session. A browser session (`previewSessions`: `{ pid, exp, seat }`) lasts 12 hours from the newest link it entered (a fresh link in a browser already in that preview for that seat goes on in its session and renews it, `enterPreview`; a used link's redirect renews nothing), and a socket opened under it keeps the expiry the session had then (`publicPairValid` checks the pair's own `exp`), closing at it so the app opens it again under the renewed session; it lasts until its seat leaves or is dropped from the away list, or until the host stops the preview. A seat keeps its newest 4 per preview and a room its newest 256 (`keepNewestSessions`, by expiry, so a renewed one counts as new), and one older goes with its sockets. Sessions saved before seats were kept stay until they expire. A link dies with its seat: one whose seat isn't the room's now (`seatKnown`) is refused 403 and left unspent, a session's seat must still be known for it to serve (`previewSession`, `publicPairValid`), and a Leave or an away drop takes the seat's links, used or not (`revokePublic({ seat })`). `/__share/enter` with a used, unknown or expired link sends back only a browser already in that link's own preview (or the one its URL's `pid` names), never into another, else 403. Every room's previews share this one host name, so a request with `Service-Worker: script` gets 403 (none registers to outlive its room), and a browser entering without this room's `cs_pv`, whatever else it has or lacks (another room's cookie, an app's cookies, none: a quit browser drops `cs_pv` and keeps an app's storage), first gets a page with no `Set-Cookie` and `Clear-Site-Data: "cache", "cookies", "storage"`, then a second single-use link that sets the cookie and never clears again (`otherRoomsState`, `clearingPage`): a first entry costs one hop. Browsers act on `Clear-Site-Data` only over HTTPS (or on localhost), and clear those cookies for the whole registrable domain, so a self-hosted `PREVIEW_URL` wants HTTPS and a domain of its own, never a subdomain of a site people sign in to (on workers.dev, the account's subdomain is that domain). Only single-use links go in URLs. Links and cookies name the room by its preview key (`previewKey`: on Cloudflare its Durable Object's own id, `state.id.toString()`, which `previewFetch` routes with `idFromString`; on Node a random key kept with the room, made for one saved without, found through `previewRooms`), never by its id, which joins it. One made before keys names the id and still opens: the preview Worker routes any other room id with `idFromName`, as 0.11.24's did, the room takes its id on the preview path as well as its key (`namesRoom`, so such a cookie also counts as this room's and isn't cleared for), and Node's preview port looks rooms up by key, then id (`previewRoomFor`); what such a link gets back names the key. So what was made before keeps opening through a deploy in either order, while a key is routed only by this version's preview Worker (Release, step 3). The main Worker serves no preview: any `__preview` rest is 404 there, page or socket, before a room is asked. Requests go room → host's stream → the host's plugin (`sh` + `curl` against localhost, only ports it shared; above, "The public link asks") → `POST proxy/<id>` back (`proxyAnswer`: format 2 or 0.11.24's headers; malformed is 400 and over 20 MB 413, the browser getting a 502 page at once either way). At most 512 asks wait per room (`PUBLIC_LIMITS.proxied`), past which a 503 page, and the preview Worker streams a request's body to the room, which bounds it (1 MB).
  - `npx wrangler dev` runs the Worker locally (real Durable Objects and WebSockets); point the e2e at it with `EXTERNAL_SERVER=1 SHARE_SERVER=http://127.0.0.1:8787`.
- **The public server.** The plugin shares through `SERVER_URL` (`plugin/hooks/server.ts`) unless its `server` option or `SHARED_SESSION_SERVER` says otherwise. Running it:
  - **Costs** are bounded by `LIMITS` in `server/core.mjs` (enforced on Cloudflare by the `[[ratelimits]]` bindings in `wrangler.toml`, which must say the same), `ROOM_SEATS_MAX`, `ROOM_FILES_MAX`, `ROOM_FILES_COUNT`, `ROOM_PREVIEWS_MAX`, `EVENT_BYTES`, `HISTORY_BYTES`, the previews' `TCP_LIMITS` and `PUBLIC_LIMITS` (whose per-seat and per-room minute counts are in memory, like needs, not `LIMITS`) and the 24 h expiry. Cloudflare has no hard spending cap; a person sets a budget alert in the dashboard (Billing → Budget alerts).
  - **Stop new rooms at once:** `npx wrangler deploy --var NEW_ROOMS:off` (joining existing links keeps working); deploy again without it to reopen.
  - **End an abused room:** `curl -X POST -H "Authorization: Bearer $ADMIN_TOKEN" <server>/api/admin/rooms/<id>/end`, with the token set by `npx wrangler secret put ADMIN_TOKEN` (Node: the `ADMIN_TOKEN` environment variable).
  - **What it may say it keeps** is on its home page (`homePage` in `server/core.mjs`) and in "Privacy and the public server" in the README and `docs/guide.md`: change all of them with any change to what's stored or for how long. `node test/previews.mjs` checks the home page's sentences against the constants they name.
- **Sidebar marks never stack:** `markSidebar` strips earlier `👥 … · ` and `…'s session · ` marks (`unmarked`) before saving and marking, since a share that never unmarked (an app quitting mid-share) leaves one behind.
- **Never commit `rooms.json`, nor the `rooms.json.tcp` Node writes beside it.** The first holds room tokens, and on Node the accounts and teams too; the second holds room ids, which are what a room's link carries. `.gitignore` lists `rooms.json`.
