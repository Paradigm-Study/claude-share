# Shared Sessions guide

Share a Claude Code session with a link. Teammates open it, land in a Claude Code session of their own that is attached to yours, and talk to it. Everyone sees every prompt and every reply, live, as normal transcript rows.

- **One machine does the work.** The session that shared is the host. Every turn and every tool runs there, in its folder, under its login.
- **Everyone else is a guest.** A guest's prompt goes to the host and runs in turn, as a turn of its own. Every host turn plays out in each guest's own transcript as a prompt and a streamed reply. A guest's own model is never called.
- **The host stays in charge.** When a guest's prompt makes Claude write a file, run a command or reach the network, the host is asked first, whatever the host's permission mode, and the same goes for what an agent started by that prompt does, even after the guest's turn has ended. The question shows the exact command or diff. The host can also make the session watch-only.
- **It lives in Claude's own UI.** In Claude Desktop and the terminal:
  - a teammate's prompts carry their dot avatar and name;
  - the footer and working line say who's here and whose turn it is;
  - a Room panel has the session on top (Live, who's here, the link), then its pages: **People**, **Chat** (a side chat Claude never reads, with who came and went), **Shown** (what Claude showed) and **Settings**;
  - everyone has a color of their own, the same on their face, their name in the Room and the chat, and their prompts in your transcript;
  - in Desktop, the session list marks and pins shared sessions.
- **What Claude shows, everyone sees.** When the host's Claude opens a file in the side panel or the Files pane, draws a widget, or opens a page in the browser pane, each guest's own Claude Code opens the same thing. A local dev server it opens in the browser pane, or only gives the address of (`http://localhost:3000/…`), is the host's to give: the row above the prompt asks **Share localhost:3000 with the room?**, and only **Share** shares it, at that page (**Not now** holds for the room), since a teammate's prompt can have Claude name any port of yours. It's asked about only once a web page answers there (an API that answers with JSON or a 404, a database or a debugger isn't; one Claude opened in the browser is asked about whatever it shows, but never a debugger), and so are the ones it opened or gave out before you pressed **Share everything**, if they're still running (after **Only from now on**, only the ones since, a reopened session included). Where nothing draws that row (a `claude -p` run), none is shared; a host moved to the cloud asks its approver instead. Files are saved in the guest's project under `.shared-session/` (kept out of git). A dev server opens through its preview link unless the host explicitly allows forwarding; then each guest presses **Open preview** above the prompt (or **Open** in the Room), and it opens at the host's own address, such as `http://localhost:3000`, forwarded through the room server: in Claude's browser (in Claude Desktop) or the guest's own browser when that port is free on their computer, otherwise in a separate browser window that leaves the guest's own services on that port alone. Screenshots the host's Claude takes (the browser pane's, a computer's) and images it opens show in the guest's tool cards as they do in the host's. A page it publishes (an Artifact) arrives with its pictures and other files beside it, and opens whole in the guest's browser pane, again whenever it's opened again; nobody needs the private claude.ai link. The Room shows anyone whose plugin is out of date, and a guest who types the update command into the session has it run on their own computer. A guest's message can carry attachments (images, PDFs): they're saved in the host's project and the host's Claude opens them.

- **Teams.** Sign in with GitHub or Google, make a team, and what you share goes to it: everyone in the team sees your live sessions in their **Team** panel and joins with one press (**Join all** for every one). Teammates come in by invite link, by their email's domain or by their GitHub organization; each team says whether its sessions are for its people only or for anyone with the link.

Built as a Claude Code plugin of function hooks (a "mod"), plus a small room server that runs on Cloudflare or as a single Node process. **It works right after install:** sharing goes through a public server this project runs ([what it sees and keeps](#privacy-and-the-public-server)), and teams can point it at their own.

For the shortest path to a first session, start with the [README](../README.md#install). Commands below run from the repository root.

## Install

One line in a terminal:

```bash
claude plugin marketplace add Paradigm-Study/claude-share && claude plugin install shared-session@claude-share
```

Works in Claude Desktop and in the terminal. Requires Claude Code 2.1.286 or later: `claude update` (or `npm install -g @anthropic-ai/claude-code@latest` for an npm install); Claude Desktop includes it. On 2.1.285 it works with `"env": { "CLAUDE_CODE_ENABLE_FUNCTION_HOOKS": "1" }` in `~/.claude/settings.json` (`$CLAUDE_CONFIG_DIR/settings.json` when that's set), which the setup script sets for you. An older Claude Code answers `/share-session` with how to update. The installer mentions one optional setting (the share server); leave it, and sharing uses the public server. New sessions pick it up; quit and reopen Claude Desktop for sessions already open. (Claude Code installs third-party plugins from a marketplace it knows, hence the two steps in one line.)

**Updates.** Turn them on once: **Room → Settings → Updates → Install by themselves** (the setup script does it for you). From your next new session on, a release loads into every open session by itself, with nothing to restart: the plugin keeps a copy of itself in `~/.claude/shared-session/plugin`, named in your settings' `CLAUDE_CODE_PLUGIN_DIRS` with `CLAUDE_CODE_PLUGIN_DIR_WATCH=1`, and that copy replaces its own files with each release from this repository (Claude Code reloads a watched plugin folder when its files change). It also turns on the marketplace's auto-update. **Only when I update** stops naming the folder; new sessions then run the installed copy. One exception: if you added the marketplace from a local folder (a clone, by path), Claude Desktop runs the installed copy ahead of the self-updating one, so there a release loads only when you quit and reopen it. The Room says so and copies the command that adds the marketplace from GitHub instead. A share server also turns away versions too old to work right, and says the one command that updates them:

```bash
claude plugin marketplace update claude-share && claude plugin update shared-session@claude-share
```

**Or let the setup script do it.** It works for a person or an agent; see [AGENTS.md](../AGENTS.md). From a clone of this repo:

```bash
node scripts/setup.mjs join
```

It also handles three more cases:
- `host --server <url>` installs too, then shares through your team's server.
- `deploy` makes a server on Cloudflare.
- `check --live` has real throwaway sessions share and join, then removes them.

It stops with a `NEEDS HUMAN` line at the one or two steps that need a person. Set `CLAUDE_BIN=/path/to/claude` to use a particular Claude Code binary.

**For a whole team, nothing to type:** in your organization's managed settings (or a project's checked-in `.claude/settings.json`), add:

```json
{
  "extraKnownMarketplaces": { "claude-share": { "source": { "source": "github", "repo": "Paradigm-Study/claude-share" }, "autoUpdate": true } },
  "enabledPlugins": { "shared-session@claude-share": true }
}
```

## Use it

- **Join:** open a share link. Its page opens Claude Desktop with the link in a new session's prompt box, so you press Enter. Pasting a link into any Claude Code session works too. Joining needs the plugin and a working Claude Code installation: no separate Shared Sessions account, server setup or sign-in (except for a session shared with a team that keeps its sessions to its people).
- **Team:** press **Team** above the prompt, or type `/team`. Sign in with GitHub or Google (your browser opens and shows a code; press **Continue** there only if it matches the one Claude Code shows, and Claude Code picks the sign-in up), then make a team and send people its invite link (they paste it as a message, or open it). The panel lists the sessions shared with your team right now: **Join** joins one in the session you're in if it's fresh, or opens a new Claude Desktop session with its link ready (press Enter); **Join all** does that for every one, one after another: each session that joins opens the next. You count once, however many sessions you're in: a session you're already in (here or on another computer) isn't offered again, **Open** brings up the one on this computer, and pasting a link to a room another of your sessions is in opens that one (paste it again to join here as well). Once you're in a team, **Share** goes to it (the button says **Share with Acme**); `/share-session link`, or **What you share goes → By link alone**, shares by link only. Owners choose who joins the team's sessions (**Only people in the team**, the default, or **Anyone with the link**) and who joins the team by themselves: a verified email at a domain (`acme.com`), or a GitHub organization. An owner can add only their own email's domain (never a public one like gmail.com) and organizations they're in, so nobody can pull strangers in. **Invite someone straight into a session:** while you share (signed in), press **Invite** above the prompt: the Room opens on your teammates, each with **Invite** (or type `/invite <name>`), and **Invite again** until they've joined: it shows up for them anew, even if they'd dismissed it. Nobody in your team yet? The Room says so and copies your team's invite link. It shows up in their Claude Code within about half a minute, above the prompt ("Scott invites you" with **Join**; in a session that's itself shared or joined, a button in its row that opens the Team panel) and in their Team panel, with a desktop notification (their terminal's own where it has one, else macOS's notification centre or `notify-send`; **Team → Invites to a session → Just show them** turns it off); no link to send. In a terminal: `/team signin`, `/team create <name>`, `/team invite`, `/team invites`, `/team sessions`, `/team join <n|all>`, `/team use <name|link>`, `/team access members|link`, `/team domains …`, `/team orgs …`, `/team leave`, `/team signout`, `/team delete-account`.
- **Share:** press **Share** above the prompt, or type `/share-session`. In a session that already has prompts, it asks first whether teammates may see them: **Share everything**, or **Only from now on** (`/share-session all` or `/share-session new`). The link is copied. It goes through the public server unless you set your own (below).
- **Room:** press **Room** above the prompt, or type `/room`, for:
  - who's here (hover someone for who they are, and to @mention them; everything of theirs in the transcript lights up with them) and who Claude is working for, with what it's doing and for how long;
  - the side chat, the **Timeline** (every turn as a bar in the color of whoever asked, as tall as it took; click one to go to its prompt), **Changes** (every file Claude changed, for whom, with its diff), what was shown, and this session's numbers;
  - settings: the host's rules for everyone, and each person's own: **Sounds** (a ping when someone @mentions you and a chime when your prompt starts, by default; joins too, or none), **Said out loud** (joins and mentions in the computer's voice), a **Status line** under the prompt, where previews open (**Previews**), how **Tool calls** show, and **Updates**;
  - for the host, a teammate's call waiting in the row above the prompt, shown whole, with the same **Allow once**, **Always allow** and **Decline**.
- **In the transcript:** each prompt is under its person's name, each of Claude's replies says whom it was for, and under it everyone's reactions (👍 🎉 👀; hover a reply to react) and who has seen it. `@name` in a prompt or the chat mentions someone: a toast and a ping for them, and a reply started in their prompt box. `/who` answers with a card of who's here and what each is doing.
- **Turns:** on the host, teammates' prompts go to Claude one at a time, each as a turn of its own, in the order they came, once Claude is free: a turn already running (the host's too) finishes first. While the host's Claude waits for the host to allow a guest's call, the guests' working line says so ("Waiting for Sam to allow Bash npm test"). A prompt the host's Claude Code doesn't take (one of the host's own hooks drops it) is declined to its guest: "Sam's Claude Code didn't take this prompt, so it didn't run. Send it again."
- **Show:** what the host's Claude shows reaches everyone by itself. The host can also type `/share-file <path>` to show a file, or `/share-preview <port>` (or a local address such as `/share-preview http://127.0.0.1:3000/app` or `https://localhost:3000/`) to let teammates open a local dev server at its own address. Both are listed in the Room, where guests reopen them and the host stops previews; an open preview stays on that list however much Claude shows after it. Someone who joins later gets everything so far as it was: each earlier prompt its own turn with its reply and tool cards, a few seconds for a long session, then any preview still open.
- **Local previews:** a dev server the host shares with `/share-preview` (or **Allow forwarding** in the Room's Shown page) is forwarded once each guest presses **Open preview** above the prompt or **Open** in the Room. One shared because Claude mentioned or opened it opens through its link, never forwarded, so a guest can't reach other services on the host (a database) by getting Claude to name their port; the host is asked once whether guests may open it at the same address instead, and **Allow** forwards that port alone (what the page uses beside it is then asked about one program at a time, below). **Stop** in the Room's Shown page stops a preview for the rest of the room: Claude mentioning or opening that port again doesn't share it again, even in a reopened session, and guests' windows don't ask for it, until the host shares it again with `/share-preview`. If the server can't be told right then, nothing reaches the preview anyway, its link's pages say it has ended, and the plugin tells the server again when it reconnects (or when you press **Stop** again).
  - **In Claude's browser or your own, at the host's address.** Open forwards the page, and what it uses beside it (below), to the same port numbers on the guest's own localhost and opens the host's exact address, such as `http://localhost:3000/`, as VS Code's port forwarding does: in Claude Desktop in Claude's browser, in a terminal in the guest's default browser. **Room → Settings → Previews** chooses between **Claude's browser** (Desktop's default), **Your browser** (a terminal's default) and **Always a separate window** (next); it shows once the room forwards a preview. If Claude Desktop's auto mode doesn't let the plugin open Claude's browser, the page opens in your own browser and the plugin says so once; **Allow previews in Claude** in Room → Settings then adds one rule to `~/.claude/settings.json` (`$CLAUDE_CONFIG_DIR/settings.json` when that's set; `mcp__Claude_Browser__preview_start` in `permissions.allow`) so the next preview opens there, and that rule also lets your own Claude open pages in Claude's browser without auto mode's review. Over SSH, on Linux without a display, or with `SHARED_SESSION_NO_BROWSER=1`, no browser opens: the address is copied for you. A page's hard-coded `http://127.0.0.1:3610` backend, WebSockets, cookies and OAuth callbacks registered for the host's address work as they do on the host, in any browser (Safari too), and sign-ins stay where the browser keeps them. What it costs, said once: while the guest is in the room, those port numbers on their machine are taken, and their browser's cookies for `localhost` on those ports go to the host's servers. **Close** beside a mapping in **Room → Shown** frees that page's port and what only it uses (what every page uses stays while another page is open here, and what you opened from its own row stays); the host's **Stop** of that page frees them the same way, and Leave frees them all. This happens only when every one of those numbers is free on the guest's computer; it never stops or shadows another program. Pressing Open again while one is still starting opens nothing more.
  - **A separate window, when a port is taken.** If one of those numbers is in use on the guest's computer (often by their own copy of the same project), or the computer won't let Claude Code listen on it (on Linux, ports below 1024 need administrator rights), what Open started stops again and, on macOS and Linux with Chrome, Edge, Brave, Chromium, Firefox (140 or newer), Vivaldi or Opera (the first of those that can, one that isn't your default browser first; `SHARED_SESSION_BROWSER` names another), it starts a separate window of that browser with a profile of its own for this room, and opens the host's exact address in it. In that window, `localhost` and `127.0.0.1` reach only what the host shares, through a proxy of the window's own; nothing on the guest's machine listens on the host's port numbers, so the guest's own servers on 3000 or 3610 keep running and keep their traffic, their usual browser is untouched, and the system proxy is never changed. Other sites load over the guest's own connection, through their proxy when they have one (macOS's system proxy, or `HTTPS_PROXY`/`ALL_PROXY`), and never the guest's own network. Through a proxy, names are looked up through that proxy over DNS-over-HTTPS (Cloudflare, then Google; the guest's own lookup when neither answers), and each connection goes to the address checked, never by name: a proxy that looked a name up itself could be sent to the guest's network. So a proxy that chooses its route by name sees only addresses (below, where Google sign-in fails). Sign-ins made in the window stay in its profile: when the host is signed in (`/team`), one profile serves all of that host's sessions, so the guest signs in once for them (if another of your sessions is starting a window on it at that moment, this one waits two seconds, then uses the room's own profile); otherwise it lasts for the room. Another preview opens in the same window; Firefox hands its address only to a window on that window's own profile, so the guest's own Firefox never gets it (on Linux that goes through the desktop's D-Bus session; without one, the address is copied for pasting into the window). A page already open in the window, or one whose backend is, opens there again. If the window fails to start (the browser exits with an error, or the window's proxy or profile can't be set up), the page opens on another port instead, as below, and the note says why; if the browser starts but shows no window within ten seconds, the plugin says what else would open it, and the page opens in the window if it shows later. **Previews: Always a separate window** in Room → Settings opens the window every time, for whoever wants previews kept apart from their own browser; if it can't open then, nothing else opens the page: Open says it couldn't open the window, and changing Previews opens the page without one. The same goes when no window can open on this computer at all (Safari alone, no display, SSH) or looking for a browser failed, and **Room → Shown** says under the page that it opens in a preview window and, once it's known that none can open here, why.
  - **What the page needs beside it.** When the host shares a port, the plugin looks for other web servers run from the same project (on macOS and Linux) and asks about them above the host's prompt one program at a time (a program on more than three ports, three of them at a time), every port first: "Share localhost:3510 and 3511 too? convex-local-backend, beside localhost:3000", **Share too** or **Not now**. **Share too** shares just the ports it names, and **Not now** passes on all of them (for this room); then the next question is asked. `/share-preview`'s reply says which ones the row asks about, and for a port it doesn't (said Not now to, asked about a few minutes ago, or the row is busy) the command that shares it, such as `/share-preview 3510`. A port already shared isn't offered, and a page shared through its link that's forwarded for another page's sake stays a page of its own. Ports shared this way are marked as used by that page: **Open preview** and a late joiner's history open the page itself, never its backend, and the Room lists the backend as "Used for the preview of localhost:3000", with no **Open** or **Public link** of its own while that page is there: it opens with the page. An API Claude only mentioned isn't shared by itself, so it's among what's asked about here once the page is forwarded. If a guest's window later reaches a port the host hasn't shared, the guest is told and the request goes to the host, who is asked "Alex's preview needs localhost:3610", **Share** or **Not now**, when that port is a web server run by the host's own account, isn't a debugger, wasn't declined or stopped in this room, and wasn't asked about in the last ten minutes. A host who isn't connected isn't sent the request, and the guest is told to ask them instead. Nothing is shared without the host's click.
  - **Neither.** Without a suitable browser or a display for a window, over SSH, with `SHARED_SESSION_NO_BROWSER=1` (which opens no browser at all and copies the address instead), or when the window fails to start, a taken port can't get a window: the page then opens where it was last (or at the host's port), else at an available one, what it uses goes to the host's numbers where they're free, and one note says what that costs: a sign-in registered for the host's port won't work at the other address, and the page may reach the guest's own server on a number that's taken. Safari can't make a preview window: it has no proxy setting of its own, only the system's, which the plugin never changes. **Room → Shown** shows each mapping, with **Close**. While a preview holds a port, a server the guest starts on it afterwards either fails as busy (Linux) or, listening on every address, misses localhost requests until the preview stops (macOS).
  - **Both ways.** A small Node helper on each guest forwards TCP bytes through the room; one long-lived Node worker on the host manages all of that room's forwarded connections. Node 20+ and POSIX `sh` are needed on both machines, and the host needs its live `curl` stream. Without Node on the host, teammates' connections are refused at once and the host is told. **Public link** explicitly opens the existing public preview instead. Close, Leave or the host's Stop closes the window's connections or the forwarded ports; a restart or reload brings each forwarded port back exactly where it was, without opening a browser (one taken meanwhile stays closed, and the plugin says so), and a preview window is reopened with **Open preview**.
- **In a terminal:** the same, by keyboard. Type `/share-session` (in a session with history, `/share-session all` shares everything so far, `/share-session new` only what comes next), `/room` and `/stop-sharing`; paste a link as a prompt to join. `/room` opens the Room as a dialog: its pages are a digit away (1 People, 2 Chat, …), Tab and the arrows walk a page, Enter picks, Esc closes. The row above the prompt says who's here and whose turn it is, and its buttons take focus like the rest of the prompt area. A guest's transcript draws the host's tool calls the terminal's way: runs of reads, searches and commands fold into one line ("Searched for 2 patterns, read 3 files"), edits and the rest get their own `Update(notes.txt)` rows, and the Room's **Tool calls: Each shown** draws every call with its result; the host's prompts show as `Name: …` under the terminal's own "Prompt from the shared-session plugin" line. What the host's Claude shows reaches a terminal guest as a saved file or a link to open in a browser.
- **Stop:** press **Leave**, or **Stop sharing** twice (it ends the room for everyone), or type `/stop-sharing`. Esc in a guest stops the shared turn.
- **Restarting is fine.** If the host quits Claude Code (to update, say), the room stays open: guests see the host away, and what they type meanwhile is answered there, not run. Reopening the same session (Claude Desktop does it after a restart, and also when you go on from an earlier message; `claude --resume` in a terminal) picks the room back up on the same link. `/clear` ends it, as Stop sharing does. While a reopened session picks its room back up (usually under a second), Share, Join and what you type wait for it, and the row above the prompt shows no Share. If the room isn't back after 10 seconds (the share server is slow to answer, say), they go on without it while the session keeps trying to get back in, and Share appears again. What a host types then goes to this session's Claude. What a guest types gets a note instead ("Still getting back into Alex's session, so this didn't go to Claude. Send it again in a moment."), so it never runs on the guest's own Claude: that note is the turn's last word, and the guest's own Stop hooks don't run for it. Sharing anew then, joining another session here, or pasting a session's link gives the old room up instead, once the new one is shared or joined: a room you shared ends, and a room you joined is left. If the new one can't be shared or joined (the server refuses it, or doesn't answer), nothing is given up, and the old room comes back the next time this session starts. In a session with earlier prompts, Share asks first which to share, and only your answer gives the old room up: Cancel leaves it to come back. From the moment you press Leave or Stop sharing, what you type is your own again and nothing you type goes to the room, even while the plugin is still closing it. A Share, `/share-session` or a pasted link meanwhile waits for the close to finish, however long the share server takes to hear it, then goes on. If an update in place interrupts the close, the plugin finishes it as it loads again, rather than take the room back up. A guest who restarts is back in the room when their session reopens, still pinned, with what they missed played in; **Leave** leaves for good. A guest whose laptop slept or lost its network for a while comes back by themselves too: the room shows them as having lost connection, then back.
- **Connection:** if the room can't be reached, the row above the prompt says it is reconnecting; anything sent meanwhile goes out once it's back.


## Privacy and the public server

Out of the box, Share uses `https://claude-share.proud-limit-da0a.workers.dev`, run by this project ([its page](https://claude-share.proud-limit-da0a.workers.dev/)). Joining a link always uses the server in that link.

- **What it sees:** while a session is shared, its prompts and the files people attach to them, Claude's replies and, while someone else is in the room, its thinking as it happens (passed along, never kept), the tools it runs with the first lines of their results and the pictures in them (screenshots, images Claude opens), the side chat, people's reactions to Claude's replies and which replies each person has had on screen, files or local previews the host's Claude shows, and messages between a teammate's own other sessions and the host's session, and what became of them, which go to the other side alone (passed along, never kept). **What Claude shows → Stays with me** keeps the pictures and files on the host's machine. Sharing a session that already has history asks first whether to include it; everything means everything the session stored, from before any compaction too (its newest 4,000 rows).
- **How long:** a room and everything in it is deleted 24 hours after the host stops sharing or was last seen. A room keeps its newest 5,000 events, 16 MB of them at most. For forwarded (TCP) previews the room keeps only coarse connection and traffic-budget counters until then; a connection keeps nothing, and closes when its seat leaves or the host stops the preview. For a preview opened through its link, the room keeps the link (which preview, which seat made it, the page it opens) for 10 minutes, and the browser session it starts (which preview and seat) for 12 hours from the last link that browser opened; both end when that seat leaves or the host stops the preview. A seat keeps its newest 4 browser sessions per preview, and a room its newest 128 links and 256 browser sessions. A link or session that expired is removed at the room's next activity, or with the room; one that ended goes at once. Application bytes are relayed, never stored. To count the rooms each network makes in a day, the server on Cloudflare keeps a hash of each new room's network address, keyed by a random key made for that day, with that count, until the day (UTC) ends; then all of it goes, the key too. No analytics, no request logs.
- **Previews share a host name:** every shared session's previews are served on one preview host name, and their links name the session by a key of its own, which can't join it. A browser not already in a session's previews has that host name's storage and cache, and its domain's cookies, cleared before it enters; browsers clear them only over HTTPS (or on localhost). No preview can register a service worker there. Clearing can't stop a page that's still open, though: a preview page of one session left open in a browser can reach the previews of another session that browser opens after it. Close the previews of a session you don't trust before opening another's, or open them in a browser profile of their own. A server of your own can give each session's previews a host name of its own, which closes this ([A host name per room](#host-a-server)).
- **Accounts, only for teams:** sharing and joining need none. Sign in to use teams, and the server keeps your name, username, verified email, the GitHub organizations you're in, your teams and their settings, which open sessions are shared with each team, and invites to a session (who invited whom to which, kept until joined, dismissed, the session ends, or 12 hours). Signing in finishes only when you press Continue on the server's page. The page and Claude Code show the same code, and you continue only if they match. Until you press Continue, the server keeps who GitHub or Google said you are; after ten minutes that sign-in stops working, and it's deleted then. Claude Code's token is made when it picks up the sign-in, and the server keeps only its hash, never the token itself. All of it stays until you delete your account (`/team delete-account`), which removes it at once. Signed in, a session you share or join also knows your account for as long as it lasts, so your sessions count as one person. On your machine, the sign-in (for each server, Claude Code's token for your account, who you are, and which team Share goes to) is in `~/.claude/shared-session/account.json` (under `CLAUDE_CONFIG_DIR` when set), readable only by you.
- **Local room recovery:** your machine keeps the room credentials and session state needed to resume in private files under `~/.claude/shared-session/rooms` (under `CLAUDE_CONFIG_DIR` when set). Forwarded previews are recovered by their host and local ports, never by worker-control credentials. Stopping, leaving or consuming a saved checkpoint deletes it. These files are separate from the plugin code and are not uploaded as diagnostics.
- **Preview window profiles:** a guest's preview window keeps its cookies and sign-ins in a browser profile of its own under `~/.claude/shared-session/browser` (under `CLAUDE_CONFIG_DIR` when set), readable only by you, which is what keeps them private: a Chrome-family window encrypts them with a fixed key rather than one from your Keychain or keyring, so it never asks for those. For a host who is signed in, there is one profile for all of that host's sessions on that server: it is kept when you leave, so you stay signed in to their apps, and deleted after 30 days unused (or delete that folder yourself). Otherwise the profile is the room's: kept while you may come back to the room and deleted when you leave, the room ends, or `/clear` or a logout ends your place; leftovers older than a day are swept at the next session start. Nothing in either is sent anywhere by the plugin.
- **Finding what a preview needs:** on the host, the plugin lists its own computer's listening ports and the folders their programs run in, and asks those ports for a page, only on that computer. A guest's request for a port goes to the host's live stream and is not kept by the server.
- **Who can see it:** anyone with the room's link; for a session shared with a team that keeps its sessions to its people, only people in that team. It's encrypted in transit, not end to end: the server can read what passes through it.
- **Limits:** per network, 6 new rooms and 30 joins a minute; per room, 20 people, 100 MB of files (10,240 at most), 128 open previews, events (a prompt, a reply's row, a chat line) of 128 KB each and 900 posts a minute; a signed-in account makes at most 30 changes a minute to its teams and invites. A preview's link takes request bodies up to 1 MB and responses up to 20 MB, with 512 requests waiting per room, 32 WebSockets per seat and 128 per room (one the host doesn't take up within 10 seconds closes, and those waiting hold 8 MB per room at most), and 30 new links a minute per seat (120 per room). A room sends out at most 8 GB a day of its files and of what its previews' links answer, and to any one seat at most 256 MB a minute of it. Such a WebSocket closes once 1 MB sent through it waits unread; on Cloudflare, which can't see that, once one side sends more than 4 MB in a second. Forwarded previews have the limits under [Limits](#limits). Abused rooms get ended.

To keep sessions on your own infrastructure, run your own server (below) and set it in the plugin's `server` option or `SHARED_SESSION_SERVER`.


**In the cloud.** A host's **Move to cloud** sends the session's project (the files git tracks, and untracked ones it doesn't ignore), its conversation, and the host's Claude token (from `claude setup-token`) to a container the server starts for that room, over its own connection, never a public address. The server passes them on and keeps none of them; the container's Claude Code runs as the host on the host's Claude plan. The container, and everything in it, is deleted when the host brings the session home, the room ends, or a week after the move; what it changed is kept as a room file for Bring home (deleted with the room). Revoke the token at claude.ai to stop it anywhere.
## Host a server

Teams can run their own room server instead of the public one. Rooms are short-lived: they expire 24 hours after the host was last seen, and nothing is kept after that.

**Cloudflare (recommended):** a Worker with one Durable Object per room. A quiet room costs nothing: open streams end at the Worker, and the room sleeps between changes. It fits the free plan for a small team. From a clone of this repo:

```bash
node scripts/setup.mjs deploy
```

That signs you in (`npx wrangler login` in a browser), deploys and waits for the server. It then points this machine at it and prints the one-line install for teammates. By hand, it's `npx wrangler login`, `npx wrangler deploy`, then `npx wrangler deploy -c wrangler.preview.toml`. To update a server already deployed, go the other way round: `npx wrangler deploy -c wrangler.preview.toml` first, then `npx wrangler deploy` (new rooms' preview links need the new preview Worker, which still opens the old ones). `setup.mjs deploy` does it in that order and stops if the preview Worker doesn't deploy, before the main one changes. The second Worker serves previews of a host's localhost on a host name of its own. On workers.dev every room's previews share it, and a browser not already in a room's previews has that host name's storage, cache and cookies cleared as it enters; browsers clear those cookies for the whole domain, which on workers.dev is your account's subdomain, so another Worker of yours there that keeps cookies loses them in that browser too. Sharing one host name has a cost clearing can't cover: a page from one session's previews still open in a browser can make requests to another session's previews that browser opens later, and read them. Give each room's previews a host name of its own (next) to close that.

**A host name per room** (recommended where people you don't all trust share sessions on one server): a domain of its own on your Cloudflare account, never a subdomain of a site people sign in to, such as `example-previews.dev`. These steps are a person's, in the Cloudflare dashboard:

1. Add the domain to Cloudflare, and on it a proxied DNS record named `*` (an `AAAA` record to `100::` is the usual stand-in; the Worker answers, not that address). Its free certificate covers `*.example-previews.dev`, one level deep, which is all this needs.
2. In `wrangler.preview.toml`, add `routes = [{ pattern = "*.example-previews.dev/*", zone_name = "example-previews.dev" }]`, and set `PREVIEW_URL = "https://*.example-previews.dev"` under `[vars]` there and in `wrangler.toml`.
3. Deploy as above: previews first, then the main Worker.

Each room's previews are then served at `<room>.example-previews.dev`, an origin of their own (its first part names the room by a key that can't join it), with no clearing hop as a browser enters. Links made before the change stop working; open the preview again. Pages there can still set cookies for the whole domain from their own scripts (the server strips a Domain from cookies an app's answers set), which other rooms' previews then receive; nothing on that domain should rely on its cookies.

**Anywhere else:** any machine with Node 20 behind HTTPS.

```bash
PORT=8787 PUBLIC_URL=https://share.example.com DATA_FILE=./rooms.json node server/node.mjs
```

Previews are served on a second port (`PREVIEW_PORT`, default `PORT` + 1); set `PREVIEW_URL` to how people reach it, on a domain of its own, such as `https://example-previews.dev`. Every room's previews share that host name, and a browser not already in a room's previews has the cookies of that whole domain cleared as it enters, so it must never be a subdomain of a site people sign in to; browsers clear them only over HTTPS (or on localhost), so serve it over HTTPS. Better, give each room's previews a host name of its own: point a wildcard name (`*.example-previews.dev`, with a wildcard certificate) at the preview port and set `PREVIEW_URL=https://*.example-previews.dev`. The server then names each room's previews by that first part, as on Cloudflare (above).

**Teams on your own server** need sign-in, from GitHub, Google or both. Make an OAuth app and give the server its id and secret:

- **GitHub:** Settings → Developer settings → OAuth Apps → New OAuth App. Homepage URL: your server. Authorization callback URL: `https://<your server>/auth/github/callback`. It asks for `read:user user:email read:org` (the organizations are for teams that let a GitHub organization in; an organization that restricts third-party apps lists only once an owner approves the app).
- **Google:** Google Cloud console → APIs & Services → Credentials → Create credentials → OAuth client ID → Web application. Authorized redirect URI: `https://<your server>/auth/google/callback`. Scopes: `openid email profile`.

On Cloudflare, `npx wrangler secret put GITHUB_CLIENT_ID` (and `GITHUB_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`). On Node, the same names as environment variables; accounts and teams are kept in `DATA_FILE` with the rooms. A server with neither has no sign-in, and teams aren't offered on it.

**Then point Claude Code at it**, by its `https://` address (plain `http://` works only for a server on the same computer, `localhost` or `127.0.0.1`: anywhere else it would carry everyone's room tokens and sign-ins unencrypted, so the plugin refuses it). Use any one of these:

- run `/plugin configure shared-session` and enter the address;
- set `SHARED_SESSION_SERVER` in the `env` block of `~/.claude/settings.json` (`$CLAUDE_CONFIG_DIR/settings.json` when that's set), or in your organization's managed settings so a whole team gets it;
- in your own fork, bake the address in with `node scripts/set-server.mjs https://your-server`.

## Security model

- **The link is the key.** Room ids are 128-bit random values; anyone holding a link can join while the host shares. Names are self-declared: `git config user.name`, else the computer's username.
- **A team can keep its sessions to its people.** A session shared with a team whose setting is **Only people in the team** lets in only people signed in with an account in that team, checked against the team as it is at each join. Someone who leaves the team, or is removed from it (deleting their account included), leaves its sessions at that moment, every session of theirs in them; and a team set to **Only people in the team** lets go of whoever joined its sessions by link before. Sign-in uses the provider's verified email for domains, and GitHub's own membership list for organizations. A GitHub and a Google sign-in with the same verified email are one account, but only while that account still has the address: an address it moved from signs nobody in to it, and a second account at the same provider with that address (one deleted and made again for someone else) gets an account of its own. Claude Code opens the sign-in page with only a hash of a secret it keeps, and collects the sign-in with that secret, so a sign-in link seen elsewhere can't be used to take it. Since anyone can make a sign-in link, nobody is signed in until they press **Continue** on the server's own page, which shows the same code as Claude Code. That page can't be shown inside another site's frame, and Continue works only once the page has been in front for a moment and the pointer has moved over it (or a key was pressed), so a click timed from another page can't press it.
- **The server relays plaintext.** It sees the shared transcript: prompts, replies, tool calls and results. Run it somewhere you trust.
- **Guests can't act on the host's machine without the host.** By default, only reads inside the host's project run without asking, as they really are: a read through a link in the project that leads out of it (a repository's own, say) asks, as does one whose place can't be told. A guest's request to read anywhere else, edit, run commands or use the web asks the host first. An agent a guest's turn starts counts as that guest's, even after the turn ends, and while a guest's turn runs, the host's own agents' calls are asked about as that guest's too. "Always allow" trusts one person for the session, and allows their calls already waiting, except one whose dialog is up, which waits for its own answer. It trusts that person, never a name: someone else who joins as "Alex" is still asked, while Alex's other sessions, signed in to the same account, are trusted too. The host can require approval for every tool, or none. The question comes up in Claude Code's own dialog, one call at a time, each showing its own command or diff (cut at 40 lines, with how many more). Where that can't show (a settings hook that takes AskUserQuestion, say), it's asked in the row above the prompt instead, in the terminal or Claude Desktop: the oldest call first, with how many more wait, and beside it what its one line leaves out ("+2 lines", "12 → 14 lines"), which opens the Room on the whole call. Where no row is drawn either (VS Code alone, or a `claude -p` run), the call is declined. A call is never answered for the host: one left ten minutes in the row, one still waiting when sharing stops, and one waiting when the plugin reloads (an update in place) are declined.
- **What Claude shows travels too, unless the host keeps it.** Files Claude shows, and the pictures in its tool results (screenshots, images it opens; the newest 60 results' worth from a shared history), go through the server (10 MB each, 100 MB and 10,240 files a room, deleted with the room). The host can keep them in Room → Host controls.
- **Previews are for the room only.** A localhost listener's connections carry your seat's token in the room, which the server checks as each one opens. The token stays in helper memory and its outer WebSocket authorization header, never browser URLs, process arguments, saved mappings or application bytes. Both IP families bind only loopback; the server and host verify the exact shared preview/target port, never a guest-selected network destination. Close, Stop, Leave or the room's end closes its connections. This is transparent TCP forwarding, not an HTTP firewall: the application must still validate Host/Origin and protect against CSRF/DNS rebinding. A preview forwarded to your computer isn't shared on from your other sessions: when you host a session yourself, the plugin won't share or forward a port another session's preview holds here, whether your Claude mentions or opens it or you ask with `/share-preview`, Allow forwarding or Share too, and it refuses teammates' connections to a port shared earlier that such a preview holds now. Where it can't tell who holds a port (no Node, a system it can't read, a listing that takes too long), it shares as before. It can't stop your own tools (ssh, ngrok, a proxy) from passing it on. **Public link** is separate: a link lasts ten minutes and lets in only the first browser that uses it, whose session lasts twelve hours from the newest link that browser opened, ends when you leave or the host stops the preview, and is one of at most four per seat and preview. A link, used or not, stops working once the session that made it leaves the room. The host's Claude Code fetches each request from its own localhost with the request's Origin and Referer set to that local address, as the page's own would be; cross-site requests are kept out by the link's cookie, which is host-only and SameSite=Lax. Every shared session's public previews share one host name, and their links name the session by a key that can't join it; a browser not already in that session's previews has that host name's storage, cache and cookies cleared before it enters (browsers do it only over HTTPS, or on localhost), and no preview can register a service worker there. Browsers clear those cookies for the whole domain, so a preview host name of your own (`PREVIEW_URL`) belongs on a domain of its own.
- **A preview window is its own browser.** It runs with a profile of its own and a proxy only it uses, never the system's or your usual browser's settings. Its loopback addresses reach only the ports the host shares, and only by `localhost`, its subdomains or a loopback address: another name that points at your computer (`lvh.me`, or a site's own name turned to 127.0.0.1) is refused, so no page can read the host's previews under a name of its own. Your own addresses, your local network (private addresses such as 192.168.x.x and 10.x.x.x, and the subnets your machine is on, IPv6 included), link-local and cloud-metadata addresses are refused, so a host's page can't reach your services or your network through it. Set `SHARED_SESSION_PREVIEW_LAN=1` where Claude Code starts if a page legitimately needs a private address on your network (an office service, say); link-local and metadata addresses stay refused. Everything else leaves from your machine as your usual browser's traffic does. With a proxy of your own, a name your machine can't resolve is passed to that proxy to resolve, as your browser would. The proxy listens on 127.0.0.1 with no credentials of its own and never holds room tokens; the plugin's control key for it travels only on its stdin and in a local request header. The window opens only when you press Open, and closing it is done by the process that holds its profile, never by matching other programs. WebRTC goes only through the proxy too (TURN over TCP), with no UDP of its own: Firefox by the window's settings, a Chrome-family browser by its profile's own setting (`disable_non_proxied_udp`), written before each start. `node test/local-preview.mjs` checks this in real Chrome and Firefox windows.
- **Application cookies stay in each guest's browser.** The helper forwards that request's cookies, not a shared application login jar. Browser profiles remain separate, but localhost cookies are **not isolated by port**: an app using the same cookie names can collide with other localhost apps. In Claude's browser or your own, its `localhost` cookies for the forwarded ports go to the host's servers, and the host's app sets its own there; a preview window has a profile of its own (one per signed-in host, or per room), so its cookies never mix with your usual browser's. Choose **Previews: Always a separate window** in Room → Settings to keep them apart every time.
- **Previews carry WebSockets.** Local TCP previews preserve the application's complete WebSocket handshake, including its Cookie, Authorization and Origin headers, and stream SSE or HMR without HTTP buffering. The explicit public gateway still uses its existing Node WebSocket relay, which does not forward application Cookie or Authorization headers; without Node on the host, that public gateway can serve HTTP but not its sockets, and refuses them at once.
- **Only what a person types travels, and their own sessions' messages.** Desktop's hidden context notes are stripped from prompts before they leave a machine. A guest's message from another of their own Claude sessions on the same computer (`SendMessage` to the joined session) goes on to the host's Claude as a message from that session ("Agent… · via Scott"), and the host's Claude answers it with its own `SendMessage`, which goes through the room to that guest alone and on to that one session, and so on back and forth; the room shows it as relayed ("Scott relayed a message from Agent…"). The guest's Room → Settings → **Messages from my other sessions → Stay here** keeps them. Its address stays on the guest's computer: the room sees only a random handle for it, and on the host's computer the plugin answers for it at a socket of its own beside the host's session's (Node 20 or later, macOS or Linux, and Claude Code 2.1.304 or later on both computers). Claude Code's own rules apply at each end as between any two sessions: a message from a session in another permission mode class (bypass against default, accept edits or auto) waits until its person lets it in (or that session's user settings say `crossSessionInbound: "accept"`), loops between sessions are cut, and the session that sent a message hears what became of it (held, let in, dropped). On the host's side such a message is the host's Claude's like any session's: the host's permission mode decides what it may run, not the approval a teammate's prompt asks for. When it can't go (the host away, watch-only, a Claude Code older than 2.1.304 on either side), that session is told instead. A Slack or OpenClaw channel's message, a background task's or a schedule's stays in the guest's session. A link relayed by another session, a channel or a task never joins anything.

## Limits

- **Guests' tool cards are replays.** The host's tool calls show in a guest's transcript as tool cards (Bash, Read, Edit…) with the host's results, drawn by the plugin's own `replay` tool, which runs nothing. Each result is cut to its first 40 lines; its pictures come whole. A guest's session lists that tool while joined.
- **Not mirrored:** subagents' inner steps. Guest image and PDF attachments travel as room files as described above.
- **No "Alex is typing…".** The engine doesn't see keystrokes in Claude Desktop's composer.
- **Needs `curl` for live updates.** Each shared session keeps one `curl` process reading the room's stream, so a quiet room makes no requests. Without `curl`, or against a server too old to stream, the plugin polls instead, from every 0.4 s while busy down to every 15 s when quiet.
- **Failed host turns:** guests see a note in the reply when the host's turn errors or is refused.
- **Local TCP previews have bounded resources.** The host plugin, dev server and guest session must stay open. Each seat has at most 32 pending or active TCP connections across all its previews; each room and its single host worker have at most 64, and each guest listener accepts at most 32 sockets. New connections have a minute budget of 240 per seat and 1,200 per room. A room has a 1 GiB lifetime traffic budget, reserved in 1 MiB blocks per direction; closing a connection gives back its unused reservation. Each direction allows at most four outstanding 64 KiB chunks; parser/send queues and control output waiting to be acknowledged remain bounded to 1 MiB, however long a connection lives. Legitimate half-closed TCP connections stay open until both directions and their credits finish; reaching a limit refuses or closes that connection rather than dropping bytes or expiring the whole guest listener. A connection is let in by your seat in the room, and lasts as long as it does: leaving, or the host stopping the preview, closes it; if the room lets your seat go for good (a long sleep), press **Open** to reconnect. A broken TCP stream is never restored or replayed, including OAuth callback POSTs.
- **The public link has bounds of its own.** A request body carries at most 1 MB and a response 20 MB (past it, the browser gets a page saying so), and the host's app has 25 seconds to answer. The host's Claude Code fetches 16 requests at a time and holds 256 more, the room holds 512 waiting, and past either the browser gets a busy page. Each seat has at most 32 of the link's WebSockets open or waiting and a room 128; the host relays 32 at a time, and one it doesn't take up within 10 seconds closes. What waiting sockets send before the host takes them up is held to 8 MB a room, and a socket closes once 1 MB it sent waits unread (on Cloudflare, which can't see that, once one side sends more than 4 MB in a second). A socket whose app on the host fails closes with an error the page sees (1011), not as if it had ended normally. A seat mints at most 30 links a minute (a room 120) and keeps its newest 16 (a room 128), the oldest going first.
- **A message is at most 128 KB.** A prompt or a chat line past that isn't sent, and the plugin says so; the host's own rows are cut to fit instead.
- **OAuth needs the app's own registration.** In Claude's browser, your own and a preview window, the page keeps the host's address, so a redirect URI registered for the host's `http://localhost:3000/…` works for guests too; in a window, each guest signs in once per host who is signed in, or once per room. Only when a port is taken and no window can open does the page move to another port, where the redirect URI must match the actual local port. An app can make other addresses work for guests who can't use a window: register a callback for each port they may land on as well, where the provider allows several, or route every sign-in through one fixed callback that sends the person back to the address it started from (the pattern Auth.js's `redirectProxyUrl` uses for preview deployments). Browser SameSite/Secure rules, test-user allowlists and account permissions still apply. Absolute redirects, fixed HMR URLs and hard-coded HTML/JavaScript URLs are not rewritten.
- **What's shown opens by itself when allowed, except forwarded previews.** Those always wait for the guest's **Open preview** or **Open**. A guest can choose in the Room to be asked first for other shared items, and a shared external link always asks. Auto mode can refuse the browser pane, for what the host's Claude shows and for the plugin's own Open: the replay then offers the Room's **Open**, and Open uses your own browser (a shared page, the Files pane) until **Allow previews in Claude** allows it. A forwarded preview never falls back to its public link by itself. A terminal guest gets a saved file or a browser link instead of a viewer.
- **The public link serves `https://` dev servers too.** The host's Claude Code reaches its own `https://localhost` without checking that dev server's own certificate (it's the host's machine, and the server's certificate is usually self-signed); the browser sees the preview host name's certificate.
- **An update pauses an open preview window.** When the plugin updates in place, the window's proxy restarts on the same port; the browser waits a little before using it again, from a few seconds to about a minute, then carries on by itself.
- **Preview windows need macOS or Linux and Chrome, Edge, Brave, Chromium, Firefox 140 or newer, Vivaldi or Opera,** not from a snap. They open in a separate window, not Claude Desktop's browser pane, which can't take a proxy. On macOS the window is a second copy of its browser, and macOS treats the two as one app: while the window is open and your own copy of that browser isn't, links you open in other apps go to the window, and the browser's Dock icon brings the window forward rather than starting yours (with yours open first, links keep going to yours). So the window takes a browser that isn't your default when there's another one (Edge or Firefox when Chrome is your default, say), and it's worth quitting (⌘Q) when you're done. Elsewhere (Safari alone, no display, SSH) previews still open at the host's numbers when their ports are free (in Claude's browser or your own; with no display or over SSH, the address is copied), and a taken port moves the page instead. Each preview window counts against the same 32-connection limit per guest, idle browser connections included.
- **Session list changes are Desktop-only.** The 👥 title and the pin use Claude Desktop's own sidebar tools. Elsewhere they're skipped. In auto mode (Desktop's default for new sessions), Claude Code refuses a plugin's pin unless an allow rule covers it; after a refusal, a **Pin** button shows in the row above the prompt (and **Allow pinning** in the Room's Settings), and pressing it once adds allow rules for exactly those sidebar tools to `~/.claude/settings.json` (`$CLAUDE_CONFIG_DIR/settings.json` when that's set). Shared sessions pin themselves from then on, and ones left unpinned pin within a minute.

Add `EXTERNAL_SERVER=1 SHARE_SERVER=https://your-server` to run it against a deployed server instead of a local one, or `SHARED_SESSION_TRANSPORT=poll` to test the polling fallback. The no-model TCP checks also accept an external server: with `wrangler dev --local` running, use `EXTERNAL_SERVER=1 SHARE_SERVER=http://127.0.0.1:8787 node test/local-preview.mjs` to exercise the actual Worker runtime.

The end-to-end run starts a host (in bypass mode, on purpose) and two guests, then checks:
- sharing and joining;
- history and attribution;
- live replies, and that guests never call a model;
- ordering;
- Esc from a guest;
- that everyone hears the room over one open stream;
- that a file the host shares lands in the guest's project, that explicit public preview tickets carry HTTP and WebSockets, and that a dev server Claude mentions, or gave out before Share, isn't shared without the host's yes (a `-p` run has no row to ask in);
- that forwarded previews tell live and late guests to press **Open preview** or **Open**, without opening a window, starting a listener or falling back to a public link automatically;
- that a guest's write is refused without approval;
- that sharing ends cleanly.

`claude plugin test plugin` runs `plugin/tests/`: the UI tests (`band.test.tsx`) drive the Room's **Open**, **Open preview** and **Close**, Claude's browser and auto mode's refusal of it, the preview window's launch, its profile's launch lock, proxy routes and lifecycle, the host's suggestions and questions, the public link's fetches and relays on the host, port selection, per-channel warnings, every way out of a room, the host's answers to a teammate's calls (the dialog, the row, their order, a reload), teammates' prompts taking turns, and host worker lifecycle; `window.test.ts`, `preview.test.ts`, `proxy.test.ts` and `upstream.test.ts` test the pure modules beside it. `node test/local-preview.mjs` uses the production helpers and host worker to check real TCP forwarding, alternate local ports, concurrent guests/previews, half-closes, overload recovery, backpressure and disconnects without replaying POSTs; when Chrome, Edge, Brave or Chromium is installed (or `SHARED_SESSION_TEST_CHROME` names one), it also opens a headless window with the production flags, and when Firefox is (or `SHARED_SESSION_TEST_FIREFOX` names one), a headless Firefox with the production settings; in each it checks the host's origin, a secure context, a hard-coded `127.0.0.1` dependency, cookies, WebSockets and SSE, and that an unshared port is refused, while the guest's own servers on the same ports get nothing. On a Node that runs TypeScript itself (22.18 or newer), it also runs the plugin's own window probe against each: it must find that one process by its profile, and its close must end it. Then it checks WebRTC in each, started as the plugin starts it: nothing reaches a STUN server or made-up peers at this machine's own address directly, and TURN over TCP goes through the proxy. That holds short-lived listeners on the machine's first network address for about 10 seconds per browser, and is skipped without a network address, with macOS's firewall on, or without the browser. It also relays WebSockets to an `https://` dev server through the public link's relay (when `openssl` can make it a certificate). `node test/browser-proxy.mjs` checks the proxy's SOCKS5 handling, routing, upstream proxies and control port; `node test/discover.mjs` checks discovery against real processes in a temporary project. `node test/previews.mjs` checks the server's preview shares, who may connect to a forwarded one, Stop, needs, what's shared, the public link's links, browser sessions, sockets and answers, the shared preview host name's protections, bounded bodies and events, what's saved across restarts and that the home page says what the server keeps, on a real Node server too. `node test/tcp-worker.mjs` checks Worker hibernation/admission, the Worker's public link, its files and preview links, a deploy of the two Workers in either order, and Node rejection races without a model. `node test/teams.mjs` checks accounts, teams and the sign-in's confirmation page; when Chrome, Edge, Brave or Chromium is installed (or `SHARED_SESSION_TEST_CHROME` names one), it presses Continue in it, headless, as a person would and as a click timed from another page would, and skips that check otherwise. `node test/setup.mjs` checks the setup script against a fake CLI in a temporary home, the order it deploys the two Workers in included.
