# Native subscription pool enrollment

The native Mac helper may enroll using the person's existing Claude Share sign-in. No separate invite token is needed for an actual member of the configured team. The helper still needs a one-time install on each Mac. Claude continues making requests directly in native subscription mode; this bridge authorizes enrollment and membership checks, and does not proxy inference.

The deployment operator sets `NATIVE_POOL_TEAM_ID` to one exact existing Share team ID and `NATIVE_POOL_URL` to the pool's HTTPS origin. An email domain, current team selection, a similarly named team, and a team's **Anyone with the link** room setting do not grant pool access. The account and its membership row must exist in the configured team. Removing either configuration value disables authorization.

The local helper generates a random verifier, keeps it locally, and sends its lowercase SHA-256 hex digest and a device name to authenticated `POST /api/native-pool/enrollment`. Only the keys `challenge` and `device_name` are accepted, in a body no larger than 2 KiB. Names are 1–80 characters with no controls or surrounding whitespace. The Share bearer token is sent only to the Share origin that issued it.

Share returns a random 32-byte base64url `grant`, `expires_at` in epoch seconds, the configured `pool_server`, and the team's ID and name. The helper sends the grant and verifier to that configured pool. Share stores only the grant's SHA-256 hash, alongside the account and team IDs, device name, verifier hash, pool origin and expiry. Grants expire after 120 seconds, are consumed once, and are deleted by the directory alarm even if no client returns. At most five grants per account may be outstanding. Enrollment also counts against the existing account change and network limits. Proofs and sign-in tokens never go in URLs or logs.

The pool uses a private cross-script Durable Object binding to this worker's `DirectoryObject`, with the singleton name `directory`:

- `POST /rpc/consumeNativePoolGrant` with JSON `[grant, verifier, poolServer]` returns `{result:{ok:true, account_id, team_id, device_name, expires_at}}`, or `{result:{ok:false,status,error}}`. The grant is bound to the configured pool origin, and account, team and membership existence are checked again when it is consumed. Concurrent consumption succeeds once.
- `POST /rpc/nativePoolMembership` with JSON `[accountId, teamId, poolServer]` returns `{result:{ok:boolean}}` only when the bridge configuration agrees with the requested team and pool. Bare `ok:false` means the account, team or actual membership no longer exists and the pool may revoke the device. Missing bridge configuration or disagreement returns `{result:{ok:false,status:503,error}}`; malformed account input returns a structured `400`. Any structured error or transport failure must pause credential delivery without revoking membership. The pool checks this before assigning credentials or accepting account contributions, including after provider operations that wait.

These two paths are accepted only by the private object. The public worker does not forward any `/rpc/` route. Other existing directory operations continue using their existing Durable Object methods. A binding is the authorization boundary; do not add a public route or an arbitrary RPC dispatcher.

Share never receives Claude subscription credentials through this bridge. The separate coordinator owns the pool credentials and devices; its retention and revocation rules are documented in [Claude Desktop Swap](https://github.com/Paradigm-Study/claude-desktop-swap). Leaving Share's configured team stops future access through membership checks. It cannot retract a Claude access token already delivered to a Mac before that removal; that token remains subject to its provider expiry or revocation. Changes to an external GitHub organization or email domain do not by themselves remove an existing Share membership: remove that membership in Share when access should end.

Validation: `npx vitest run test/native-pool.test.ts` covers membership, strict inputs, expiry, verifier binding, replay and concurrent consumption, account removal, grant limits, alarm cleanup and the public/private routing boundary.
